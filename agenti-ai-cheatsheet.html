Le leve per
migliorare un agente

Riferimento rapido da consultare prima di qualsiasi intervento. Parti dal sintomo, identifica la leva, applica i principi chiave. Per l'approfondimento, consulta i report specifici.

Sezione 1
Mappa delle leve

Le leve non sono indipendenti — si influenzano a vicenda. Il prompt definisce come usare i tool; il RAG fornisce contesto che il prompt usa; il testing valida tutto. Capire i legami evita di ottimizzare una leva senza sapere che il problema è a monte.

Dipendenze e legami funzionali tra le leve
Principali legami tra leve — cosa influenza cosa
RAG
→ alimenta →
Prompt
Il contesto recuperato viene iniettato nel prompt. La qualità del retrieval determina la qualità della risposta.
Prompt
→ governa →
Tool
Il system prompt istruisce quando e come usare ogni tool. Una gerarchia mal scritta produce invocazioni errate.
Tool
→ abilita →
Orchestrazione
L'orchestrazione coordina sequenze di tool calls. Tool mal progettati rendono inutile qualsiasi pattern di orchestrazione.
Memoria
→ estende →
Prompt + RAG
Il profilo semantico e gli episodi recuperati vengono iniettati nel context. La memoria è RAG sulla storia dell'utente.
Testing
→ valida →
Tutte le leve
Ogni modifica a qualsiasi leva va misurata sulla suite di test. Senza testing non sai se stai migliorando o peggiorando.
Fine-tuning
→ potenzia →
Prompt + RAG
Il FT modifica il comportamento base su cui il prompt opera. Va fatto dopo aver ottimizzato prompt e RAG, non invece di farlo.
Sezione 2
Schede leve
01
Prompt Engineering
Identità · obiettivo · ragionamento · formato · esempi · casi limite
↺ Reversibile in minuti · Sempre attiva
"Mostra il comportamento con esempi — non descriverlo con istruzioni."
Decisioni chiave
Identità prima di tutto. Ruolo specifico + contesto operativo + interlocutore. Orienta ogni risposta successiva.
Operazionalizza l'obiettivo. Non "analizza il contratto" ma "estrai le clausole penali e calcola l'esposizione massima". Output descritto, non task generico.
Istruzione esplicita per ogni edge case critico. Il modello non inferisce le eccezioni. Se un comportamento è critico, scrivilo esplicitamente con l'alternativa.
CoT per ragionamento complesso. "Pensa passo per passo prima di rispondere" migliora la coerenza su task multi-step senza costo aggiuntivo.
Passa alla leva successiva quando
Il comportamento non migliora nonostante prompt ottimizzato + esempi few-shot. Oppure il prompt supera 5.000 token e il costo/latenza diventano un problema strutturale.
02
Scelta del Modello
Triangolo intelligenza / velocità / costo · routing per task
↺ Reversibile in ore/giorni
"Non si sceglie il modello migliore — si sceglie il più adatto alle dimensioni critiche del task."
Decisioni chiave
Identifica le 2–3 dimensioni critiche prima di guardare i modelli. Ragionamento? Velocità? Costo per operazione? Output strutturato? Instruction following su edge case?
Valuta sul tuo task, non sui benchmark pubblici. 50–100 casi reali > qualsiasi leaderboard per prevedere le prestazioni reali.
Routing: modelli diversi per task diversi. 70% small + 30% large riduce i costi del sistema dell'80% rispetto all'uso uniforme del modello più capace.
Passa alla leva successiva quando
Il modello ha già il profilo giusto per il task e il problema persiste. Non è il modello il collo di bottiglia.
03
Tool Design
Nome · descrizione (cosa/quando/NON quando) · parametri · output · error contract
↺ Reversibile in ore
"Esponi intenzioni semantiche, non endpoint tecnici. La description conta più del codice."
Decisioni chiave
La description risponde a 3 domande: cosa fa, quando usarlo, quando NON usarlo. La terza è la più trascurata e quella che previene gli errori più costosi.
Il rischio determina il livello di guardrail. Tool lettura: poca istruzione. Tool comunicazione/scrittura irreversibile: istruzione ridondante nello schema E nel prompt + HITL.
Output pulito: il tool_result torna nel context window. ID tecnici, errori HTTP e JSON verboso degradano la risposta. Restituisci solo ciò che il modello deve usare.
Ogni azione irreversibile richiede conferma esplicita. Senza eccezioni. Il pattern: mostra → verifica → esegui.
Passa alla leva successiva quando
I tool funzionano ma l'agente risponde con informazioni non aggiornate o non nel suo training. Il problema è la conoscenza, non le azioni.
04
Knowledge / RAG
Indicizzazione · retrieval · augmentation · valutazione separata per stadi
↺ Reversibile in giorni
"Il problema di qualità è quasi sempre nel chunking — non nel modello di retrieval."
Decisioni chiave
Chunking prima di tutto. Un chunk autonomo: "letto da solo risponde a qualcosa di utile?" Se no, ridisegna la strategia di chunking. Il 90% dei problemi RAG nasce qui.
Ricerca ibrida > semantica pura. Semantic search fallisce su codici, ID, acronimi. BM25 fallisce su sinonimi. La fusione (RRF) è quasi sempre superiore.
Istruzioni di grounding nel prompt. Tre casi obbligatori: risposta nel contesto, risposta assente ("non hai abbastanza informazioni per rispondere"), risposta parziale.
Valuta retrieval e generazione separatamente. Context recall basso → problema di indicizzazione. Faithfulness bassa → problema di augmentation/grounding.
Passa alla leva successiva quando
Il sistema risponde male su task che richiedono coordinazione tra molti step o più agenti specializzati — non mancanza di conoscenza.
05
Orchestrazione
Loop agentic · pattern composizione · topologie multi-agente · stato · HITL
↺ Reversibile in settimane
"Un agente singolo ben configurato batte quasi sempre un sistema multi-agente mal progettato."
Decisioni chiave
Ogni loop deve avere un limite massimo di passi. Il loop infinito è il failure mode più comune in produzione — non è un crash, è un loop che non converge. Imposta sempre un tetto esplicito.
Singolo prima di multi-agente. Ottimizza il singolo agente fino ai suoi limiti prima di aggiungere complessità. La complessità deve comprare qualcosa di misurabile.
Lo stato è la mappa, l'output è il territorio. Non usare gli output come proxy dello stato. Un schema di stato esplicito è il prerequisito di qualsiasi recovery da fallimento parziale.
HITL per le decisioni che solo l'umano può prendere. Troppi checkpoint = alert fatigue. Ogni richiesta di approvazione deve mostrare: cosa/chi/rischio/cosa succede se rifiuti.
Passa alla leva successiva quando
L'orchestrazione funziona ma l'agente non mantiene coerenza tra sessioni diverse o dimentica informazioni importanti tra un turno e l'altro.
06
Testing e Valutazione
Suite di test · metriche per task · LLM-as-judge · ciclo di iterazione
∞ Attiva subito · In parallelo a tutto
"Non si migliora ciò che non si misura. La suite di test è più importante del prompt."
Decisioni chiave
30% casi limite nella suite. I casi tipici mostrano la media. I casi limite mostrano dove il sistema si rompe — e si rompono spesso proprio lì in produzione.
Dev set + held-out set sempre separati. Il prompt ottimizzato solo sul dev set è sovraadattato. Il gap dev/held-out > 8 punti segnala overfitting.
LLM-as-judge: valida su campione umano prima di usarlo. Il giudice ha bias (verbosity, self-enhancement, position). Correlazione con giudizio umano ≥ 0.85 prima di affidarsi a lui.
Soglie prima di misurare. Decidi il target accettabile prima di vedere i dati. Altrimenti giustifichi qualsiasi risultato a posteriori.
Non si "passa" a questa leva
Va attivata al primo prompt e mantenuta attiva indefinitamente. Ogni modifica a qualsiasi leva va misurata. Non è una fase — è un'infrastruttura permanente.
M
Gestione della Memoria
In-context · episodica (tra sessioni) · semantica (profilo) · procedurale (comportamenti)
↺ Reversibile in giorni
"Memorizza decisioni e preferenze — non dettagli e contenuto. La memoria minima necessaria è la più robusta."
Decisioni chiave
4 tipi diversi, 4 meccanismi diversi. In-context (sessione corrente), episodica (eventi tra sessioni), semantica (fatti stabili sull'utente), procedurale (comportamenti nel prompt).
Compressione progressiva prima del troncamento. Quando il context window si avvicina al limite, summarizza i turni vecchi. Il troncamento produce degradazioni silenziose.
La memoria è un default sovrascrivibile. L'input corrente ha sempre la precedenza. Il profilo memorizzato non è un vincolo — è un punto di partenza.
Privacy by design. Non memorizzare dati sensibili (salute, convinzioni), includere TTL su ogni elemento, garantire il diritto alla cancellazione.
Passa alla leva successiva quando
La memoria funziona ma ci sono comportamenti sistematici difficili da correggere con il prompt — stili, pattern di ragionamento, expertise tacita.
07
Fine-tuning
Stile/formato · ragionamento di dominio · comportamento/allineamento · DPO
↺ Poco reversibile · Settimane/mesi
"Il FT insegna come rispondere — non cosa sa. Per aggiungere conoscenza, usa il RAG."
Decisioni chiave
Ne hai davvero bisogno? Il test: scrivi 10 esempi dell'output che vuoi. Un collega riesce a scrivere un prompt che li produca? Se sì, non serve il FT.
Parti dal tipo 1 (stile). Stile → ragionamento di dominio → comportamento (DPO). Non partire dal tipo 3 senza che i primi due siano stabili.
La qualità del dataset è tutto. 100 esempi eccellenti battono 1.000 mediocri. Ogni esempio deve passare il test: "un domain expert lo userebbe come modello?"
Testa la regressione sui task non ottimizzati. Il FT amplifica i pattern degli esempi e può degradare i comportamenti non rappresentati nel dataset.
Ultima leva da toccare
Solo dopo aver ottimizzato prompt, modello, tool, RAG e orchestrazione. Il costo reale include: manutenzione del dataset ad ogni cambio requisiti, gestione delle regressioni, lock-in del vendor.
Sezione 3
Diagnostica rapida

Parti dal sintomo — non dalla leva. Usa questa sezione per capire dove intervenire quando qualcosa non funziona. Per ogni gruppo di sintomi, trovi la leva da attivare e l'azione concreta da fare.

⚡
L'output è sbagliato o incoerente
Qualità risposta
Risponde bene nella demo, male nei casi reali
es: funziona su esempi tipici, fallisce sugli edge case
→
Testing
Aggiungi casi limite alla suite. Il 60% degli errori in produzione avviene lì.
Inventa fatti o cita fonti inesistenti
es: allucina nomi, date, numeri non presenti nei documenti
→
RAG + Prompt
Aggiungi contesto via RAG. Nel prompt: "rispondi solo se nel contesto fornito".
Il tono / stile / formato non è quello che vuoi
es: troppo formale, troppo verboso, struttura sbagliata
→
Prompt (Cluster D + E)
Specifica il formato output con esempi concreti (few-shot). Non descrivere, mostrare.
Ignora istruzioni specifiche o vincoli
es: risponde lo stesso pur avendo detto di non farlo
→
Prompt (Cluster F)
Sposta le istruzioni critiche alla fine del system prompt. Aggiungi "in nessun caso" per i guardrail assoluti.
Il ragionamento è superficiale su task complessi
es: risponde senza motivare, salta passaggi logici
→
Prompt (Cluster C)
Aggiungi chain-of-thought esplicito: "Prima analizza X e Y, poi concludi". Fornisci il framework di analisi.
📚
Non sa quello che dovrebbe sapere
Conoscenza e contesto
Risponde male su informazioni specifiche del dominio
es: non conosce i tuoi prodotti, le tue procedure, i tuoi documenti
→
RAG
Indicizza il corpus e aggiungi retrieval. La conoscenza va nel contesto, non nel modello.
Non ricorda informazioni dette in precedenza nella stessa sessione
es: dimentica preferenze espresse all'inizio di una conversazione lunga
→
Memoria (in-context)
Implementa summarization progressiva. Le info critiche devono stare vicino alla fine, non al centro del contesto.
Non ricorda nulla tra sessioni diverse
es: l'utente deve ripetere le proprie preferenze ad ogni sessione
→
Memoria (episodica + semantica)
Implementa estrazione episodica a fine sessione e profilo semantico iniettato all'avvio.
Usa informazioni obsolete o sbagliate
es: risponde su normative o dati che sono cambiati
→
RAG (aggiornamento corpus)
Aggiorna il corpus indicizzato. Il RAG garantisce che le informazioni siano aggiornabili senza re-training.
⚙️
Problemi nell'uso dei tool e nelle azioni
Tool e azioni
Usa il tool sbagliato o non lo usa quando dovrebbe
es: cerca nel web invece del database interno, o viceversa
→
Tool Design (description)
Aggiungi "quando NON usare" nella description. Scrivi la gerarchia di preferenza nel system prompt.
Invoca il tool con parametri sbagliati o incompleti
es: ID errati, campi obbligatori mancanti, enum non validi
→
Tool Design (parametri)
Aggiungi esempi validi/invalidi nei parametri. Descrivi i valori enum e i casi speciali.
Compie azioni irreversibili senza chiedere conferma
es: invia email, cancella record, modifica dati senza verifica
→
Tool Design + Prompt G
Aggiungi HITL obbligatorio. Istruzione nel prompt: "mostra → verifica → esegui" per ogni azione irreversibile.
Non gestisce correttamente gli errori del tool
es: continua dopo un errore, non riprova, non segnala il problema
→
Tool Design (error contract)
Definisci l'error contract: codice errore + significato + azione attesa (retry/stop/escalate).
🏗️
Problemi di sistema e architettura
Architettura e performance
Il sistema è troppo lento o costa troppo
es: latenza inaccettabile, costo per operazione non sostenibile
→
Scelta modello (routing)
Introduce routing: modello small per task semplici (70–80% del volume), large solo per i task complessi.
Task complessi falliscono perché troppo lunghi per un singolo turno
es: analisi di 50 documenti, pipeline multi-step che si spezza
→
Orchestrazione
Scomponi in workflow con stato esplicito. Prima prova con un singolo agente + loop; multi-agente solo se necessario.
Il workflow si blocca o entra in loop infinito
es: l'agente continua ad agire senza convergere
→
Orchestrazione (terminazione)
Imposta limite massimo di passi e rilevamento di stallo (stesse azioni per N iterazioni → stop).
Comportamento sistematico impossibile da correggere col prompt
es: stile sbagliato malgrado istruzioni molto dettagliate, expertise tacita
→
Fine-tuning (tipo 1 o 3)
Solo dopo aver ottimizzato tutte le altre leve. Scrivi 10 esempi gold e verifica che nessun prompt li produca.
🔍
Non sai dove è il problema
Triage iniziale
Stessa domanda → risposta diversa ogni volta
es: output inconsistente anche su task identici
→
Testing (coerenza)
Misura la varianza su 10 esecuzioni identiche. Se alta: riduci temperatura, aggiungi output schema esplicito nel prompt.
Non sai se un cambiamento ha migliorato o peggiorato le cose
es: hai cambiato qualcosa ma non sai se era giusto farlo
→
Testing (suite + metriche)
Costruisci una suite di test con metriche definite prima di iterare. Senza di essa stai ottimizzando alla cieca.
In una nuova sessione funziona bene, in quella lunga no
es: degrada progressivamente nel corso di conversazioni estese
→
Memoria (context saturo)
Il system prompt finisce nel "lost-in-the-middle". Implementa summarization progressiva a partire dal 60–65% del context window.
Cinque principi da tenere sempre a mente
01
L'ordine delle leve è una gerarchia di costo. Esaurisci la leva meno costosa prima di passare alla successiva.
02
La qualità dei dati precede la qualità dell'algoritmo. Vale per RAG, fine-tuning, testing.
03
La semplicità è un valore. La complessità aggiuntiva deve comprare qualcosa di misurabile.
04
Valuta sul tuo task, non sui benchmark. 50 casi reali battono qualsiasi leaderboard pubblico.
05
I sistemi evolvono. Golden dataset, pipeline di eval e documentazione delle decisioni sono ciò che li rende mantenibili.
