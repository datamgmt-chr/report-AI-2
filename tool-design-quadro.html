Introduzione

Cos'è un tool — la definizione operativa

Un tool è qualsiasi capacità che il modello può invocare esplicitamente per interagire con il mondo esterno o eseguire operazioni che la generazione di testo da sola non può fare.

Un modello LLM, nella sua forma base, fa una sola cosa: data una sequenza di token in input, produce una sequenza di token in output. Questo è potente — ma insufficiente per la maggior parte degli agenti di interesse pratico. Un agente che deve cercare informazioni aggiornate, eseguire calcoli precisi, scrivere un file, inviare un'email o interrogare un database non può farlo con la sola generazione di testo.

I tool colmano questo gap. Un tool è una funzione con interfaccia definita — nome, descrizione, parametri, output — che il modello può invocare come parte del suo processo di ragionamento. Il modello non esegue il tool direttamente: genera una richiesta di invocazione strutturata, il sistema runtime esegue la funzione, il risultato viene restituito al modello come contesto per il passo successivo.

Questa architettura è deliberata. Il modello rimane nel suo dominio (il linguaggio e il ragionamento); il tool opera nel suo dominio (i sistemi, i dati, il mondo reale). La separazione dei ruoli è ciò che rende il sistema sicuro e controllabile.

La definizione operativa
Un tool non amplia ciò che il modello sa — amplia ciò che il modello può fare. La distinzione tra sapere e poter fare è il fondamento dell'architettura agentic.
Il RAG amplia ciò che il modello sa (porta conoscenza nel context window). I tool ampliano ciò che il modello può fare (permettono azioni nel mondo). Un agente maturo ha entrambi: RAG per la conoscenza, tool per l'azione. Confondere i due porta ad architetture sbagliate — usare un tool dove servirebbe RAG, o viceversa.
Perimetro della leva 3 — più ampio di "API esterne"

I tool non sono solo chiamate a servizi REST. Includono l'esecuzione di codice (il modello genera Python che viene eseguito), l'accesso al filesystem (lettura e scrittura di file), il retrieval come tool agentico (il modello decide quando e come cercare), e la percezione multimodale (analisi di immagini e audio). Ogni meccanismo che permette al modello di "toccare" qualcosa fuori dalla generazione di testo è un tool nel senso di questa serie.

Sezione 02

Il loop function calling — il meccanismo in dettaglio

Come il modello "vede" i tool, come decide di invocarli, cosa succede nel context window ad ogni giro del loop. Il meccanismo che sta sotto tutto il resto.

Il function calling non è magia — è un pattern preciso di interazione tra il modello e il sistema che lo ospita. Capirlo in dettaglio è il prerequisito per progettare tool e istruzioni che funzionano.

Tre aspetti del meccanismo che hanno implicazioni pratiche dirette sul design dei tool:

Aspetto
Come funziona
Implicazione pratica
Il modello "vede" i tool attraverso le loro descrizioni
Le definizioni dei tool (nome + descrizione + parametri) vengono inserite nel context window prima della query. Il modello non ha accesso al codice del tool — solo alla sua interfaccia testuale.
La descrizione è il componente più critico di ogni tool. Se è vaga o ambigua, il modello invocherà il tool nei momenti sbagliati o con i parametri sbagliati. → Report A
Il tool result diventa contesto per il ragionamento successivo
Il risultato di ogni tool call viene aggiunto al context window. Il modello lo legge e decide: rispondere direttamente, invocare un altro tool, o chiedere chiarimenti.
Il formato del risultato conta quanto il contenuto. Un risultato ben strutturato (JSON chiaro) è più usabile di uno verboso e non strutturato. → Report A (output contract)
Il loop può continuare per N cicli
Non c'è limite fisso al numero di tool call in un singolo turno. Il modello continua a invocare tool finché non ritiene di avere tutto ciò che serve per rispondere.
Senza un limite esplicito nel prompt, il modello può invocare tool in loop indefinito. Il limite di passi del Cluster G della Leva 1 è essenziale. → Report B

Sezione 03

La tassonomia — i 5 tipi di tool

Non tutti i tool sono uguali. Cinque tipi con caratteristiche diverse di sicurezza, reversibilità, latenza e complessità di design. Ogni tipo ha un report dedicato nella serie.

Tipo 01
Tool di lettura
Read-only · idempotenti · sicuri per default

Recuperano informazioni da sistemi esterni senza modificarne lo stato. Idempotenti: invocarli una, due o venti volte produce lo stesso effetto (nessuno). Il tipo di tool più sicuro — il rischio principale è la latenza, non l'impatto.

get_calendar_events(date, user_id) search_web(query, num_results) get_crm_record(id) read_file(path) get_weather(location)
IDEMPOTENTE SAFE CACHEABLE
Tipo 02
Tool di scrittura
Effetti collaterali · spesso irreversibili · richiedono cautela

Modificano lo stato di sistemi esterni. Non idempotenti: invocarli due volte produce effetti diversi (due email inviate, due record creati). Il rischio è reale — un'invocazione sbagliata può avere conseguenze difficili da annullare. Richiedono i guardrail del Cluster G.

send_email(to, subject, body) create_ticket(title, description) update_crm_record(id, fields) write_file(path, content) post_message(channel, text)
NON IDEMPOTENTE SIDE EFFECTS IRREVERSIBILE
Tipo 03
Code execution
Il modello genera codice · il runtime lo esegue · il risultato torna

Il tool più potente e più flessibile: il modello genera codice (Python, SQL, shell) che viene eseguito in un ambiente controllato. Abilita calcoli precisi, trasformazioni dati arbitrarie, automazione — qualsiasi cosa esprimibile in codice. La sicurezza dipende interamente dal sandboxing del runtime.

execute_python(code) → stdout, return value run_sql(query) → risultato tabellare bash(command) → stdout, exit code execute_js(code) → output del runtime
TURING-COMPLETE SANDBOX REQUIRED PRECISO
Tipo 04
Retrieval come tool
Il modello decide quando e come cercare · agentic RAG

Il retrieval RAG esposto come tool invece che come pipeline passiva. La differenza fondamentale: il modello decide autonomamente quando recuperare, quale query usare, e quante volte iterare. Abilita retrieval multi-step adattivo — impossibile con il RAG passivo.

search_documents(query, k, filters) get_document_section(doc_id, section) search_web(query) lookup_knowledge_base(topic)
IDEMPOTENTE ADATTIVO MULTI-STEP
Tipo 05
Percezione multimodale
Immagini · audio · documenti come immagine · video

Tool che permettono al modello di "percepire" input non testuali: analizzare immagini, trascrivere audio, leggere PDF come immagini (preservando layout e struttura visiva). Sempre più centrali con i modelli multimodali. Spesso il sostituto migliore al parsing testuale su documenti strutturati.

analyze_image(url_or_base64) transcribe_audio(file_path) parse_document_visual(pdf_path) describe_chart(image)
IDEMPOTENTE MULTIMODALE LAYOUT-AWARE
Il principio della tassonomia

La distinzione più importante non è tra i 5 tipi — è tra tool idempotenti (lettura, retrieval, percezione) e tool con effetti collaterali (scrittura, alcune invocazioni di code execution). I tool idempotenti possono essere invocati liberamente; quelli con effetti collaterali richiedono sempre un layer di controllo esplicito. Il Cluster G del prompt engineering è stato progettato esattamente per questo.

Sezione 04

Tool vs. Skill — due meccanismi distinti

Una delle distinzioni più sottili e più importanti dell'intera serie. Tool e skill non sono sinonimi — sono due meccanismi diversi per ampliare le capacità di un agente, e scegliere quello sbagliato produce sistemi meno affidabili.

Tool
Capacità esterna — invocata esplicitamente
Un tool è una funzione con interfaccia definita che il modello invoca con una chiamata esplicita. Il modello genera i parametri, il sistema esegue, il risultato torna nel context window. L'esecuzione avviene fuori dal modello.

Il modello sa di stare usando un tool — lo sceglie deliberatamente dalla lista dei tool disponibili, passa i parametri corretti, e riceve un risultato strutturato.
Il modello decide di cercare informazioni e invoca esplicitamente: search_documents("policy rimborsi 2024") → Il sistema esegue il retrieval → Il risultato torna nel context window → Il modello usa il risultato per rispondere
vs
Skill (capacità latente)
Capacità interna — attivata dal contesto
Una skill è una capacità codificata nel prompt o nel training che il modello attiva implicitamente in risposta al contesto. Non c'è invocazione esplicita — il modello applica la skill come parte del suo processo di ragionamento naturale.

Il modello non "usa" la skill nel senso di invocarla — la applica come farebbe un esperto umano che ha interiorizzato una competenza.
Il system prompt include istruzioni su come analizzare un contratto legale. Quando l'utente invia un contratto, il modello applica automaticamente il framework di analisi codificato nel prompt — senza invocare nessun tool esplicito. → La skill è latente nel prompt → Si attiva con il contesto giusto

La regola di scelta
Se richiede dati o azioni fuori dal modello → tool. Se richiede solo ragionamento, stile o conoscenza linguistica → skill nel prompt. Se richiede entrambi → skill nel prompt + tool per la parte esterna.
La skill nel prompt è sempre preferibile al tool quando è sufficiente — è più semplice, non aggiunge latenza, non ha failure mode di connessione. Il tool è necessario quando la skill da sola non può completare il task. La combinazione dei due — skill che governa il ragionamento, tool che accede ai dati — è il pattern più comune e più potente degli agenti maturi.
Sezione 05

Reversibilità e impatto — la mappa di rischio

Non tutti i tool hanno lo stesso profilo di rischio. La matrice di reversibilità è il prerequisito per progettare guardrail adeguati per ogni tipo di azione.

Prima di costruire qualsiasi sistema agentic, ogni tool dovrebbe essere classificato sulla sua reversibilità — quanto è difficile annullare gli effetti di un'invocazione sbagliata. Questa classificazione determina il livello di guardrail necessario: da nessuno (tool idempotenti) a conferma esplicita obbligatoria (azioni irreversibili ad alto impatto).

Tool / Azione Reversibilità Livello di guardrail Pattern consigliato
Lettura dati (get, search, read) ✓ Completamente reversibile — non modifica nulla Nessuno — invoca liberamente Default: nessun controllo aggiuntivo. Eventuale caching per efficienza.
Scrittura bozza / draft ✓ Reversibile — la bozza non ha effetti finché non è approvata Basso — mostra la bozza all'utente Crea bozza, mostra all'utente, attendi approvazione prima di finalizzare.
Aggiornamento record esistente ~ Parzialmente reversibile — record precedente spesso recuperabile Medio — mostra cosa cambierà Mostra il before/after prima di confermare. Log dell'aggiornamento per audit.
Invio email / messaggio ✗ Irreversibile — il messaggio è già stato ricevuto Alto — conferma esplicita obbligatoria Mostra anteprima completa + destinatari. Attendi "confermo" esplicito. Mai auto-inviare.
Creazione record / ticket ~ Parzialmente reversibile — il record può essere eliminato Medio — mostra cosa verrà creato Mostra preview del record prima della creazione. Elimina automaticamente se non confermato entro N minuti.
Eliminazione record / file ✗ Spesso irreversibile — dipende dal sistema Alto — conferma esplicita + verifica Mostra esattamente cosa verrà eliminato. Richiedi digitazione esplicita del nome per confermare. Soft-delete quando possibile.
Esecuzione codice (lettura) ✓ Reversibile se il codice non ha side effect Basso — mostra il codice prima di eseguire Mostra il codice generato prima dell'esecuzione per trasparenza. Sandbox obbligatorio.
Esecuzione codice (scrittura su sistema) ✗ Potenzialmente irreversibile Alto — revisione obbligatoria del codice Mai eseguire codice che modifica il filesystem o sistemi esterni senza revisione umana esplicita del codice generato.
Transazioni finanziarie ✗ Irreversibile o difficilmente reversibile Massimo — doppia conferma + log Doppia conferma (prima mostra, poi "sei sicuro?"), log immutabile, notifica a terzi. Limite di importo per l'autonomia del modello.
La regola assoluta — già stabilita nel Cluster G

Ogni azione classificata come "irreversibile" richiede sempre conferma esplicita dell'utente prima dell'esecuzione, senza eccezioni. Non "quasi sempre", non "salvo casi ovvi" — sempre. Questa regola va codificata nel system prompt e non può essere derogata da istruzioni dell'utente nel corso della conversazione. Un agente che viola questa regola anche una sola volta in produzione è un agente non deployabile.
