Sezione 01

Pattern di composizione dei tool

I tool raramente operano in isolamento. Quattro pattern fondamentali per combinarli — ognuno con le sue implicazioni su ordine, dipendenze, latenza e gestione degli errori.

Un agente maturo non usa tool singoli in modo indipendente — li compone in sequenze, li esegue in parallelo, li condiziona su risultati precedenti, o li itera finché una condizione è soddisfatta. Questi quattro pattern coprono la quasi totalità dei casi reali. Capirli serve sia a progettare il sistema sia a documentare il comportamento atteso nel system prompt.

Pattern 01
Sequenziale — output di A è input di B
I tool si eseguono in ordine. L'output di ogni tool diventa input del successivo. Il modello aspetta il risultato prima di invocare il passo seguente. Se un passo fallisce, la catena si interrompe.
get_user(id) → [user_data] create_ticket(user_data.email, title) → [ticket_id] send_confirmation(user_data.email, ticket_id) → [done]
Quando: task con dipendenze strette tra passi. Ogni output alimenta il successivo. Errori bloccano la sequenza.
Pattern 02
Parallelo — più tool senza dipendenze reciproche
Più tool si invocano contemporaneamente quando i loro output sono indipendenti — nessuno deve aspettare l'altro. Riduce la latenza totale al tempo del tool più lento invece della somma.
Insieme: search_internal_docs(query) search_web(query) get_user_context(user_id) → [doc_results, web_results, user_ctx] Poi: sintetizza i tre risultati insieme.
Quando: più fonti di dati indipendenti, nessuna dipendenza tra tool call. Ottimizza la latenza totale del loop.
Pattern 03
Condizionale — il tool successivo dipende dal risultato
Il modello valuta il risultato di un tool e sceglie il passo successivo in base al valore ricevuto. Permette branch logic nell'esecuzione dell'agente senza hardcodare ogni percorso.
check_ticket_status(id) → if status == "open": escalate_ticket(id, reason) → if status == "resolved": send_satisfaction_survey(email) → if status == "pending": add_note(id, "In attesa risposta")
Quando: comportamento dell'agente dipende dai dati, non dalla query originale. Il modello adatta il percorso dinamicamente.
Pattern 04
Iterativo — ripete finché una condizione è soddisfatta
Il modello invoca lo stesso tool (o una sequenza) più volte finché il risultato soddisfa un criterio. Tipico per paginazione, retry, o retrieval raffinato. Richiede sempre un limite esplicito.
page = 1 loop (max 5 iterazioni): results = list_records(page=page) process(results) if not results.has_next_page: break page += 1 → [tutti i record processati]
Quando: paginazione, retry con backoff, retrieval iterativo che raffina la query. Limite di iterazioni obbligatorio nel prompt.
Il principio della composizione
I pattern non si escludono — si combinano. Un agente maturo usa sequenziale, parallelo, condizionale e iterativo nello stesso task, ognuno dove è più appropriato.
Un task di analisi contrattuale potrebbe: invocare in parallelo il retrieval di documenti interni e il profilo del cliente (parallelo), poi analizzare il contratto sequenzialmente con i dati recuperati (sequenziale), poi scegliere se escalare o rispondere in base al risk score (condizionale), poi iterare sulla ricerca se i primi risultati sono insufficienti (iterativo). Identificare quale pattern si applica a quale passo è parte del design del system prompt.
Sezione 02

Skill pipeline — tool compositi come unità

Quando una sequenza di tool viene usata ripetutamente e rappresenta un'operazione logica autonoma, vale la pena astraarla in una skill pipeline invocabile come unità singola.

Una skill pipeline è una funzione di ordine superiore: una sequenza di tool — eventualmente con logica condizionale, trasformazioni intermedie e gestione degli errori — esposta come se fosse un singolo tool. Dal punto di vista del modello che la invoca, è un tool come gli altri. Dietro ha una pipeline.

Il vantaggio non è solo l'astrazione — è la riusabilità e la coerenza. Invece di istruire ogni agente su come eseguire la stessa sequenza di passi, la logica è codificata una volta nella pipeline e riusata ovunque.

Quando astrarre vs. quando lasciare i tool singoli
Astrai in skill pipeline quando
3+ passi che rappresentano un'operazione logica coerente.

La sequenza è riusata in più agenti o in più contesti dello stesso agente.

La logica di orchestrazione ha condizioni e fallback che sarebbe verboso ripetere in ogni system prompt.

Il task ha un nome naturale che gli utenti e i developer capiscono senza spiegazione ("analisi contratto", "onboarding cliente").
Lascia i tool singoli quando
La sequenza ha 1–2 passi — l'astrazione aggiunge overhead senza semplificare.

La sequenza è usata in un solo contesto — non vale la pena centralizzare.

I passi sono altamente variabili in base al contesto — la pipeline fisserebbe troppe assunzioni.

Il modello deve poter saltare passi in base al contesto — una pipeline li rende obbligatori.
Perché funziona — astrazione come riduzione della complessità cognitiva
Chunking e riduzione del carico nel context window

Ogni tool nel context window del modello occupa spazio e attenzione. Un agente con 15 tool singoli esposti nel prompt ha un carico cognitivo molto maggiore di uno con 5 tool singoli + 2 skill pipeline che coprono gli stessi 15 tool. La skill pipeline riduce il numero di decisioni che il modello deve prendere per ogni task — non "quale dei 15 tool uso qui?" ma "uso la pipeline o un tool singolo?". Questo si riflette in scelte più coerenti e meno errori di selezione.

Sezione 03

Tool con stato — sessioni, contesto persistente, progressi

La maggior parte dei tool è stateless — ogni invocazione è indipendente. I tool con stato mantengono un contesto tra invocazioni. Più potenti, più complessi da progettare.

Un tool stateless non "ricorda" nulla tra invocazioni. Un tool con stato mantiene un contesto che evolve nel corso di più chiamate: una sessione di lavoro aperta, un processo multi-step in corso, un insieme di file modificati, un buffer di operazioni da confermare.

Le 3 regole dei tool con stato

1. Sempre session_id esplicito. Il modello deve passare lo stesso session_id a tutte le operazioni correlate. Non lasciare che il sistema gestisca la sessione implicitamente — il modello non vedrà lo stato che cambia tra invocazioni se non è nel risultato di ogni tool call.

2. Lo stato corrente nel risultato di ogni operazione. Ogni tool call su una sessione aperta deve restituire un riepilogo dello stato corrente — non solo il risultato dell'operazione. Questo permette al modello di ragionare correttamente su cosa ha fatto finora nella sessione.

3. Cleanup obbligatorio — esplicito o automatico. Ogni sessione aperta deve avere una chiusura. Progettare un timeout automatico (es. chiusura dopo 30 minuti di inattività) e documentarlo al modello — così sa che non può aspettarsi che la sessione sia ancora aperta dopo un lungo periodo.

Quando i tool con stato sono necessari — e quando sono overkill

Necessari quando: le operazioni successive dipendono dallo stato accumulato da operazioni precedenti (editing di documenti, transazioni multi-step, processi di approvazione), o quando il costo di ricostruire il contesto a ogni invocazione è proibitivo.

Overkill quando: le operazioni sono indipendenti e il risultato non dipende dallo storico, o quando la sessione durerebbe meno di 3–4 invocazioni — in quel caso il pattern sequenziale stateless è più semplice e altrettanto efficace.

Sezione 04

Model Context Protocol — cos'è e perché esiste

MCP è uno standard aperto proposto da Anthropic per definire, esporre e distribuire tool in modo interoperabile tra sistemi e modelli diversi. Il problema che risolve è reale: ogni sistema che usa tool oggi li reinventa da zero.

Oggi, ogni sistema agentico definisce i propri tool in modo proprietario. Un tool scritto per Claude non è direttamente usabile con GPT-4 o con Gemini. Un tool scritto per un agente non è direttamente distribuibile a un altro agente. Non esiste un formato standard per descrivere un tool, esporlo su rete, gestire l'autenticazione, o comunicare le sue capacità a un modello che non l'ha mai visto.

MCP (Model Context Protocol) è la risposta a questo problema. Definisce un protocollo standard che permette a qualsiasi client (un agente, un IDE, un workflow builder) di scoprire, connettersi e usare qualsiasi server MCP (un sistema che espone tool) — indipendentemente dal modello LLM sottostante e dall'implementazione specifica.

MCP definisce tre tipi di capability che un server può esporre: tools (funzioni che il modello può invocare — il focus di questa serie), resources (dati e contenuti che il modello può leggere, come file o database), e prompts (template di prompt che il server offre come punto di partenza). Questo report si concentra sui tool — la capability più rilevante per la leva 3.

Sezione 05

MCP — come funziona in concreto

Il protocollo, lo schema di un tool MCP, il processo di discovery, e come si integra con i modelli LLM moderni che lo supportano nativamente.

MCP usa JSON-RPC 2.0 come protocollo di trasporto — su stdio (per processi locali) o HTTP con Server-Sent Events (per servizi remoti). Il client invia richieste in JSON, il server risponde in JSON. La struttura è semplice e ispirata a OpenAPI.

Il vantaggio concreto: un tool, molti client

Un server MCP che espone search_internal_docs può essere usato simultaneamente da: un agente Claude nel sistema di supporto, un copilot nel IDE dei developer, un workflow builder automatizzato, e qualsiasi altro client MCP — senza dover reimplementare il tool in nessuno di questi sistemi. Il server è scritto una volta e i client si connettono tramite protocollo standard.

Sezione 06

MCP — quando adottarlo e checklist finale

MCP aggiunge valore in contesti specifici. Adottarlo quando non è necessario aggiunge complessità senza beneficio. La guida alla decisione e la checklist finale dell'intero report.

MCP non è la risposta giusta a ogni situazione. È uno standard con un costo di setup (server da mantenere, protocollo da implementare, infrastruttura aggiuntiva) che si giustifica solo quando i benefici dell'interoperabilità superano quel costo.

Adotta MCP quando
Più agenti o sistemi devono usare gli stessi tool — MCP elimina le reimplementazioni duplicate.

Tool distribuiti a terze parti o condivisi tra team diversi — il protocollo standard abbassa la barriera all'integrazione.

Ecosistema di tool in crescita — il discovery automatico scala meglio della configurazione manuale.

Modelli multipli nello stack (Claude + GPT come fallback) — MCP è model-agnostic, i tool funzionano con entrambi senza adattamenti.
Non adottare MCP quando
Un solo agente, pochi tool — il function calling nativo è più semplice e sufficiente.

Tool fortemente accoppiati al sistema specifico — l'overhead del protocollo non porta benefici se i tool non saranno mai riusati altrove.

Prototipo o POC — aggiungere MCP in fase di prototipazione è prematura optimization.

Team piccolo con un solo stack — l'interoperabilità non è un problema se tutti usano lo stesso sistema.
Lo stato attuale di MCP — Marzo 2026

MCP è stato pubblicato da Anthropic a fine 2024 ed è diventato rapidamente uno standard de facto: Claude Code, Claude Desktop, Cursor, Cline e molti altri client lo supportano nativamente. Centinaia di server MCP sono disponibili open source per i servizi più comuni (GitHub, Slack, Google Drive, database, ecc.). Per sistemi nuovi che prevedono più di un agente o più di un modello, MCP è oggi la scelta di default per l'esposizione dei tool — non più solo una tecnologia sperimentale.
