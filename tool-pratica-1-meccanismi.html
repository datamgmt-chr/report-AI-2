Come l'LLM si connette ai tool: i meccanismi

Il prerequisito per istruire correttamente un agente è capire cosa succede sotto il cofano: come l'LLM "vede" i tool disponibili, come decide di invocarli, chi esegue davvero il codice, e come il risultato torna al modello. Quattro meccanismi distinti con il loro ciclo completo.

Introduzione

Il malinteso fondamentale — l'LLM non esegue i tool

Il punto di partenza per capire qualsiasi meccanismo di connessione: il modello non ha accesso diretto al mondo. Non chiama API, non esegue codice, non legge file. Decide cosa fare — qualcosa d'altro lo fa.

L'LLM è un modello di linguaggio — prende testo in input e produce testo in output. Quando diciamo che "un agente usa un tool", quello che succede davvero è: l'LLM genera una struttura dati che descrive quale tool vuole invocare e con quali parametri. Il runtime — il codice applicativo che circonda l'LLM — intercetta questa struttura, esegue il tool, e reinietta il risultato nel contesto dell'LLM come se fosse la risposta del tool.

Questa distinzione non è accademica. Capire che il runtime è il vero esecutore è il prerequisito per rispondere alle domande pratiche: dove gira il codice Python? chi chiama l'API esterna? come si gestiscono gli errori? La risposta è sempre: il runtime — non il modello.

La separazione che governa tutto
L'LLM decide. Il runtime esegue. Il risultato torna all'LLM come testo nel context window. Qualsiasi meccanismo di connessione — tool calling, code execution, MCP — è una variante di questo stesso schema.
Questo spiega perché "dove gira il Python" è una domanda sul runtime, non sul modello. Il modello genera codice — il runtime lo esegue in un processo separato e restituisce stdout/stderr come testo. Il modello non sa che c'è un subprocess: vede solo il risultato come tool_result nel suo contesto.
Meccanismo 01

Tool calling nativo — function calling

Il meccanismo standard per collegare un LLM a tool predefiniti. L'LLM riceve uno schema JSON dei tool disponibili, genera una richiesta di invocazione strutturata, il runtime la esegue e restituisce il risultato.

Meccanismo 01
Il più usato in produzione
Tool calling nativo / Function calling
Lo schema JSON dice all'LLM cosa esiste. Il tool_use block dice al runtime cosa eseguire.

Il tool calling nativo funziona in tre momenti distinti, ognuno con attori diversi.

1
Sviluppatore → API
Definisci i tool nello schema JSON da passare all'API insieme ai messaggi. Ogni tool ha name, description, e parameters (JSON Schema). Questo schema non va nel system prompt — va nel campo tools della request API.
2
LLM → Runtime
L'LLM risponde con un tool_use block (o function_call in OpenAI) invece di testo. Contiene il nome del tool e i parametri compilati. Non è codice eseguibile — è una struttura dati dichiarativa che il runtime deve interpretare.
3
Runtime → Tool → LLM
Il runtime intercetta il tool_use, chiama la funzione corrispondente nel codice applicativo (non un'API generica — una funzione Python/JS che lo sviluppatore ha scritto), cattura il risultato, e lo reinietta come messaggio con ruolo tool o come tool_result block.
Ciclo completo tool calling — pseudocodice annotato
# ── STEP 1: DEFINISCI I TOOL (sviluppatore) ────────────────────────── tools = [ { "name": "search_documents", "description": "Cerca nei documenti interni. Usare quando l'utente chiede info specifiche. NON usare per domande generali.", "input_schema": { # Claude usa input_schema, OpenAI usa parameters "type": "object", "properties": { "query": {"type": "string", "description": "Testo da cercare"}, "max_results": {"type": "integer", "default": 5} }, "required": ["query"] } } ] # ── STEP 2: PRIMA CHIAMATA ALL'LLM ─────────────────────────────────── response = client.messages.create( model="claude-sonnet-4-5", system="Sei un assistente...", messages=[{"role": "user", "content": "Cosa dice il contratto Rossi?"}], tools=tools # ← passati qui, NON nel system prompt ) # ── STEP 3: IL RUNTIME LEGGE LA RISPOSTA ───────────────────────────── if response.stop_reason == "tool_use": # l'LLM vuole usare un tool tool_block = response.content[0] # {type:"tool_use", name:"search_documents", input:{query:"contratto Rossi"}} # ── STEP 4: IL RUNTIME ESEGUE IL TOOL (NON L'LLM) ─────────────────── tool_result = search_documents( # ← funzione Python definita dallo sviluppatore query=tool_block.input["query"], max_results=tool_block.input.get("max_results", 5) ) # ── STEP 5: REINIETTA IL RISULTATO E RICHIAMA L'LLM ───────────────── final_response = client.messages.create( model="claude-sonnet-4-5", system="Sei un assistente...", messages=[ {"role": "user", "content": "Cosa dice il contratto Rossi?"}, {"role": "assistant", "content": response.content}, # il tool_use block originale {"role": "user", "content": [{ # il risultato come tool_result "type": "tool_result", "tool_use_id": tool_block.id, "content": str(tool_result) }]} ], tools=tools )
La cosa più importante da capire

La funzione search_documents() non è magica — è codice Python normale che hai scritto tu. Può chiamare un database, un'API HTTP, leggere un file, o fare qualsiasi altra cosa. Il tool calling è un meccanismo di routing: l'LLM decide quale funzione chiamare e con quali argomenti; il runtime esegue quella funzione nel processo Python che sta girando.

Meccanismo 02

Code execution — dove gira davvero il Python

L'LLM genera codice Python (o bash, o SQL). Qualcosa lo esegue in un ambiente controllato e restituisce stdout/stderr come tool_result. La domanda "dove gira il codice" ha tre risposte con trade-off molto diversi.

Meccanismo 02
Il caso del code execution — Python, bash, SQL
L'LLM genera codice. Un processo separato lo esegue.
Il modello non esegue mai il codice direttamente. Il sandbox è il confine di sicurezza.

Quando l'agente ha bisogno di eseguire calcoli, manipolare dati, o produrre output che richiede codice, il flusso è: l'LLM genera il codice come testo, un tool di code_execution lo riceve, un processo separato (sandbox) lo esegue, l'output (stdout + eventuali errori) torna all'LLM come tool_result.

1
LLM
Genera un tool_use block per il tool execute_python con il codice come stringa nel parametro code. Il codice è testo — l'LLM non lo esegue, lo produce come output.
2
Runtime
Intercetta il tool_use e passa il codice al sandbox. Il sandbox è un processo Python isolato — con dipendenze preinstallate, filesystem limitato, timeout, e nessun accesso a rete o a risorse del sistema host (a meno che non venga configurato esplicitamente).
3
Sandbox
Esegue il codice e cattura stdout, stderr, e eventuali artefatti prodotti (file, immagini). Se il codice solleva un'eccezione, il traceback è parte dell'output. Tutto torna al runtime come stringa.
4
Runtime → LLM
L'output diventa tool_result e viene reinserito nel context. L'LLM lo legge, valuta se il risultato è corretto, e decide il passo successivo — incluso correggere il codice se ha prodotto un errore.
Esempio completo — agente che esegue codice Python con gestione errori
# Il tool execute_python definito per l'LLM tools = [{ "name": "execute_python", "description": "Esegue codice Python in un ambiente isolato. Librerie disponibili: pandas, numpy, matplotlib, requests. Nessun accesso a file di sistema. Timeout: 30s.", "input_schema": { "properties": { "code": {"type": "string", "description": "Codice Python da eseguire. Usa print() per l'output."} }, "required": ["code"] } }] # La funzione che il runtime chiama — il "sandbox" def execute_python(code: str) -> str: import subprocess, sys result = subprocess.run( [sys.executable, "-c", code], # subprocess isolato — non nello stesso processo capture_output=True, text=True, timeout=30, # sempre un timeout env={"PATH": "/usr/bin"} # env ridotto — no variabili sensibili ) if result.returncode != 0: return f"ERRORE:\n{result.stderr}" # restituisce il traceback all'LLM return result.stdout # Cosa vede l'LLM quando il codice ha un errore: # tool_result: "ERRORE:\nTraceback (most recent call last):\n File... # NameError: name 'df' is not defined" # → l'LLM legge l'errore e può correggere il codice nel prossimo tool_use

Le tre opzioni di sandbox — trade-off pratici

Opzione 01
Subprocess locale
Come: subprocess.run() con Python interpreter del sistema, env ridotto, timeout. Pro: zero infrastruttura, latenza minima. Contro: isolamento limitato, lo stesso filesystem e dipendenze del processo host.
Quando: prototipazione, ambienti fidati, codice generato a basso rischio.
Opzione 02
Container Docker
Come: immagine Docker con dipendenze preinstallate, nessuna rete, filesystem readonly tranne una directory temporanea, CPU/memory cap. Pro: isolamento reale, riproducibilità. Contro: overhead di avvio (1–3s), complessità operativa.
Quando: codice generato da utenti non fidati, produzione, dati sensibili nel sistema host.
Opzione 03
Sandbox cloud (E2B, Modal)
Come: API che riceve il codice, lo esegue in un microVM isolato nel cloud, restituisce l'output. Dipendenze configurabili. Pro: zero infrastruttura locale, isolamento massimo, scalabilità. Contro: latenza di rete (200–500ms), costo per esecuzione.
Quando: produzione scalabile, codice non fidate, necessità di dipendenze pesanti (ML, scipy).
Come istruire l'LLM sull'ambiente di esecuzione

L'LLM genera codice migliore se sa quali librerie sono disponibili, cosa può stampare, e quali sono i vincoli. Questa informazione va nella description del tool execute_python — non nel system prompt generico: "Librerie disponibili: pandas, numpy, matplotlib. Usa print() per produrre output leggibile. Timeout: 30s. Nessun accesso a file esterni." Il modello calibrerà il codice generato su questi vincoli.

Meccanismo 03

MCP — Model Context Protocol

Un protocollo aperto che standardizza la connessione tra LLM e "server di tool" esterni. Invece di integrare ogni tool manualmente nel codice applicativo, MCP definisce come un server espone tool all'LLM — e come l'LLM li scopre e li usa.

Meccanismo 03
Il protocollo emergente — standardizza la connessione
Model Context Protocol
Un server MCP espone tool con schema standardizzato. L'LLM li scopre e li usa come qualsiasi tool nativo.

Prima di MCP, integrare un tool in un agente significava: scrivere la funzione Python nel codice applicativo, definire lo schema JSON manualmente, gestire l'autenticazione, e ripetere tutto per ogni tool di ogni sistema. MCP introduce un livello di astrazione: un MCP server espone i tool con schema standardizzato; il runtime si connette al server e ottiene automaticamente l'elenco dei tool disponibili con le loro descrizioni.

La differenza pratica: invece di avere la funzione search_salesforce() nel tuo codice Python, hai un MCP server Salesforce già pronto che espone tool come search_contacts, get_opportunity, ecc. Il tuo runtime si connette al server MCP, e l'LLM vede quei tool come se fossero definiti localmente.

1
Runtime → MCP Server
Discovery automatica: il runtime chiama tools/list sul server MCP e riceve l'elenco completo dei tool disponibili con nome, description e schema parametri. Nessuna definizione manuale.
2
Runtime → LLM
I tool scoperti vengono passati all'LLM nel campo tools come in un normale tool calling. Per l'LLM è trasparente — non sa se il tool viene da un MCP server o da codice locale.
3
LLM → Runtime → MCP Server
Quando l'LLM genera un tool_use block, il runtime chiama tools/call sul MCP server con il nome del tool e i parametri. Il server esegue l'operazione reale (chiama Salesforce, legge un file, interroga un DB) e restituisce il risultato.
Connessione a un MCP server — struttura base con l'SDK Python
# Con l'SDK MCP Python (anthropic/mcp) from mcp import ClientSession, StdioServerParameters from mcp.client.stdio import stdio_client # ── Connessione al server MCP ───────────────────────────────────────── server_params = StdioServerParameters( command="npx", # server MCP come processo separato args=["-y", "@modelcontextprotocol/server-filesystem", "/allowed/path"] ) async with stdio_client(server_params) as (read, write): async with ClientSession(read, write) as session: # ── Discovery automatica dei tool ──────────────────────────────────── await session.initialize() tools_list = await session.list_tools() # [{name, description, inputSchema}, ...] # ── Converti in formato API per l'LLM ──────────────────────────────── tools_for_llm = [{ "name": t.name, "description": t.description, "input_schema": t.inputSchema } for t in tools_list.tools] # ── Usa i tool nell'LLM normalmente ────────────────────────────────── response = client.messages.create( model="claude-sonnet-4-5", tools=tools_for_llm, # tool scoperti dal server MCP messages=[...] ) # ── Quando l'LLM vuole usare un tool: esegui via MCP ──────────────── if response.stop_reason == "tool_use": tool_result = await session.call_tool( tool_block.name, arguments=tool_block.input # il server MCP esegue l'operazione reale )
Quando MCP ha senso — e quando è over-engineering

MCP è utile quando vuoi connettere l'agente a sistemi per cui esistono già server MCP pronti (Salesforce, GitHub, Google Drive, filesystem, database) — evitando di scrivere e mantenere il codice di integrazione. Per tool custom specifici del tuo dominio, il tool calling nativo con funzioni Python è più semplice e più controllabile. MCP non sostituisce il tool calling — standardizza come si espongono tool che altri hanno già costruito.

Sezione finale

Confronto e guida alla scelta

Quando usare quale meccanismo — e come si combinano nello stesso sistema.

Tool calling nativo — usa quando
✓ Hai tool custom specifici del dominio ✓ Vuoi controllo completo su ogni funzione ✓ I tool chiamano API HTTP, database, o funzioni interne già scritte ✓ Vuoi il debugging più semplice (log diretti nel tuo processo Python) Esempio: send_email(), search_crm(), create_ticket(), query_db()
Code execution — usa quando
✓ Il task richiede calcoli, data analysis, o generazione di artefatti ✓ L'LLM deve scrivere logica arbitraria non prevedibile a design time ✓ Hai bisogno di iterazione (il modello corregge il codice leggendo i propri errori) Esempio: analisi dati con pandas, generazione grafici, calcoli, trasformazione di file
MCP — usa quando
✓ Esiste già un server MCP per il sistema che vuoi integrare (Salesforce, GitHub, filesystem, Slack, Google Drive…) ✓ Vuoi evitare di scrivere il codice di integrazione da zero ✓ Vuoi aggiungere tool dinamicamente senza modificare il codice applicativo Esempio: agente che accede a GitHub Issues, legge Google Drive, e interroga Postgres via MCP
Combinare i meccanismi nello stesso agente
Un sistema agentic maturo usa spesso tutti e tre insieme: MCP → tool di sistema (filesystem, Salesforce, GitHub) Tool nativo → funzioni business custom (logiche specifiche del dominio) Code execution → calcoli, data analysis, trasformazioni dati L'LLM vede tutti questi tool nello stesso campo tools[] — non distingue quale meccanismo li serve. Il runtime orchestra tutto.
Il modello mentale da portare al Report 2
Il meccanismo determina dove vanno le istruzioni. Nel tool calling nativo, le istruzioni operative vanno nella description del tool e nel system prompt. Nel code execution, l'ambiente disponibile (librerie, timeout, vincoli) va nella description del tool execute_python. In MCP, le description arrivano già dal server — ma il comportamento d'uso si istruisce sempre nel system prompt.
Il Report 2 parte da qui: con il meccanismo chiaro, la domanda diventa "dove e come si scrivono le istruzioni affinché l'LLM usi i tool nel modo giusto". La risposta dipende dal tipo di istruzione — e non va tutta nello stesso posto.
