Le opzioni architetturali

Una volta scelto il modello (C3), la domanda diventa: dove e come lo si fa girare? Le opzioni non sono equivalenti — differiscono per profilo di sicurezza, costo, complessità operativa e tempo di attivazione. La Tab 6 di questo report fornisce la matrice decisionale per orientarsi rapidamente.

Opzione A

Cloud privato (VPC)

Il modello gira su istanze GPU di un cloud provider (AWS, Azure, GCP) in un tenant completamente isolato e gestito dall'azienda. I dati non transitano dal provider LLM ma restano nell'infrastruttura cloud aziendale.

Attivazione 1–4 settimane
Costo iniziale Basso (nessun hardware da acquistare)
Costo ricorrente Alto (GPU cloud su istanza dedicata)
Scalabilità Alta — elastica su domanda
Controllo dati Parziale — su infrastruttura AWS/Azure
Competenze DevOps cloud + MLOps base
Opzione B

On-premise

Il modello gira su server fisici di proprietà dell'azienda, nella rete interna. I dati non escono mai dal perimetro fisico aziendale. Massimo controllo, massima complessità.

Attivazione 3–12 mesi
Costo iniziale Alto (hardware GPU dedicato)
Costo ricorrente Medio (energia, manutenzione, personale)
Scalabilità Limitata — vincolata all'hardware
Controllo dati Completo — perimetro fisico aziendale
Competenze MLOps + sysadmin GPU + networking
Opzione C

Ibrido

I dati e task più critici su modello on-premise o cloud privato; task meno sensibili o che richiedono capability frontier su API provider con piano enterprise. Routing intelligente per caso d'uso.

Attivazione Variabile per componente
Costo iniziale Medio (proporzionale alla quota self-hosted)
Costo ricorrente Mix di fissi (self) e variabili (API)
Scalabilità Alta per la componente cloud
Controllo dati Selettivo — massimo per dati critici
Competenze Le più alte — gestisce due ambienti

Cloud privato: quando è la scelta giusta

Il cloud privato è la porta d'ingresso naturale al self-hosting per la maggior parte delle organizzazioni. Permette di iniziare in settimane, di scalare e ridurre le risorse in base all'uso effettivo, e di sperimentare con diversi modelli senza investimenti hardware. Il costo per ora di GPU è elevato rispetto all'on-premise a lungo termine, ma l'assenza di capex iniziale rende questa opzione accessibile per i primi progetti.

È la scelta giusta quando: si è nelle fasi di PoC o validazione, il volume d'uso è irregolare o imprevedibile, le competenze MLOps interne sono in costruzione, o si vuole rimandare la decisione sull'hardware a quando i requisiti sono chiari.

Nota CLOUD Act

Come discusso nel Report B (sicurezza dati), AWS, Azure e GCP sono provider americani soggetti al CLOUD Act USA. I dati su questi cloud — anche in datacenter europei — sono teoricamente accessibili a richieste legali americane. Per la maggior parte dei contesti manifatturieri questo è un rischio residuale, ma va valutato esplicitamente se i dati trattati sono soggetti a vincoli di giurisdizione stringenti.

On-premise: quando il controllo completo vale il costo

L'on-premise è giustificato quando il profilo di sicurezza richiede che i dati non escano mai dal perimetro fisico aziendale — e questo requisito non è soddisfacibile con garanzie contrattuali, ma deve essere una proprietà tecnica verificabile. È anche la scelta più economica a lungo termine per volumi d'uso molto alti e costanti.

I punti critici da pianificare in anticipo: la catena di approvvigionamento GPU (i server GPU enterprise hanno lead time di 3-6 mesi), il dimensionamento corretto (sovradimensionare ha un costo fisso alto, sottodimensionare limita l'uso), la ridondanza (un singolo server GPU è un single point of failure), e l'alimentazione elettrica e il raffreddamento (una A100 consuma ~400W; un cluster da 4 GPU richiede infrastruttura elettrica e termica dedicata).

Ibrido: la soluzione più razionale per molte manifatturiere

L'architettura ibrida non è un compromesso al ribasso — è spesso la scelta più razionale per organizzazioni con un portafoglio di casi d'uso eterogeneo. Il principio è semplice: ogni task usa l'infrastruttura più adeguata al suo profilo di rischio e capability.

Un esempio concreto: Q&A su manuali tecnici e classificazione non conformità su modello self-hosted (dati critici, task in zona verde) + analisi strategica e supporto alla pianificazione su API frontier con piano enterprise (task complessi, dati anonimizzati). Due sistemi, due profili di costo e rischio, ottimizzati separatamente.

Edge deployment: il caso speciale del manifatturiero

Il manifatturiero ha un caso d'uso che altri settori non hanno: il modello vicino ai macchinari. Un operatore che consulta un LLM per diagnostica o supporto operativo direttamente sulla linea produttiva ha requisiti molto diversi da un utente in ufficio: latenza minima, funzionamento offline (reti OT isolate), hardware industriale resistente, consumi energetici limitati.

Per questi scenari i modelli compatti (Phi-4 14B, Gemma 2 9B, Llama 3.2 1B-3B per task elementari) possono girare su hardware industriale come NVIDIA Jetson AGX Orin o workstation con GPU consumer. L'architettura è completamente on-device — nessuna rete, nessun server centrale, i dati rimangono sul device.

OT/IT convergence — nota importante

Portare un LLM nella rete OT (Operational Technology — reti dei macchinari) introduce rischi di sicurezza specifici che vanno gestiti separatamente dalle policy IT. Le reti OT sono tipicamente air-gapped per motivi di sicurezza funzionale. Qualsiasi integrazione di AI in ambito OT richiede una valutazione di sicurezza funzionale specifica, indipendente dalla valutazione del rischio dati.

La GPU: il componente centrale

L'inferenza LLM è dominata dalla GPU — specificamente dalla quantità di memoria GPU (VRAM) disponibile e dalla bandwidth di memoria (velocità con cui i dati vengono letti dalla VRAM). La VRAM determina quale modello si può caricare; la bandwidth determina la velocità di generazione dei token.

Una regola pratica: per ogni miliardo di parametri del modello in precisione FP16, servono circa 2GB di VRAM. In quantizzazione 4-bit (Q4), circa 0.5–0.7GB per miliardo. Quindi un modello da 70B richiede ~140GB in FP16, oppure ~40GB in Q4.

VRAM vs RAM di sistema

La VRAM è diversa dalla RAM di sistema (CPU). Il modello deve stare interamente nella VRAM per girare a velocità accettabile. Se il modello non entra nella VRAM, si può usare la RAM di sistema come overflow (CPU offloading), ma la velocità di generazione crolla a 1-3 token/secondo — inaccettabile per uso interattivo. La VRAM disponibile è il vincolo primario nella scelta del modello.

Infrastruttura di supporto per on-premise

Un server GPU non è un server tradizionale. Richiede considerazioni infrastrutturali spesso sottovalutate:

Alimentazione elettrica: un A100 consuma ~400W sotto carico. Un server con 4 GPU richiede ~2kW solo per le GPU, più CPU, RAM e storage. Verificare che il rack e il PDU (Power Distribution Unit) abbiano la capacità necessaria, e che l'impianto elettrico del datacenter o CED aziendale sia adeguato.

Raffreddamento: i server GPU generano molto calore. I rack GPU devono essere in posizioni con buon flusso d'aria o richiedono cooling dedicato. Il consumo termico (BTU) deve rientrare nella capacità del sistema di raffreddamento della sala server.

Networking: per cluster multi-GPU, la comunicazione inter-GPU (NVLink o InfiniBand) è critica per le performance. Per uso single-GPU, è sufficiente una connessione 10GbE verso la rete aziendale.

Storage: i modelli da 70B occupano 35–140GB su disco (a seconda della quantizzazione). Serve storage veloce (NVMe SSD) per il caricamento iniziale del modello e per i documenti del sistema RAG.

Cos'è la quantizzazione e perché è fondamentale

La quantizzazione è il processo di riduzione della precisione numerica con cui i pesi del modello vengono memorizzati. Un modello in piena precisione (FP16) usa 16 bit per ogni numero; un modello quantizzato a 4 bit (Q4) usa 4 bit. Il risultato: un modello da 70B che in FP16 occupa ~140GB di VRAM, in Q4 ne occupa ~40GB — rendendolo deployabile su hardware molto più accessibile.

La quantizzazione non è solo una scorciatoia per hardware limitato — è una pratica standard in produzione. La riduzione di qualità rispetto alla piena precisione è spesso minima per i task pratici, mentre il risparmio di VRAM e il miglioramento della velocità di inferenza sono significativi.

Il trade-off qualità/VRAM in pratica

La riduzione di qualità da FP16 a Q4 è spesso inferiore a quella che si avrebbe scegliendo un modello più piccolo. In altri termini: un Llama 3.3 70B in Q4 (40GB) è quasi sempre superiore a un Llama 3.3 34B in FP16 (68GB), anche se entrambi richiedono hardware simile. La quantizzazione permette di usare modelli più grandi — e quindi più capaci — su hardware dato.

Il punto di degrado percepibile varia per task: su classificazione e estrazione strutturata, Q4 è praticamente indistinguibile da FP16. Su ragionamento complesso e generazione di testi lunghi e coerenti, il degrado può essere più visibile — ma in genere rimane contenuto con i formati di quantizzazione moderni (AWQ, GGUF Q4_K_M).

Raccomandazione pratica

Q4 con formato GGUF (K_M o K_L variants) o AWQ è il punto di partenza per quasi tutti i deployment di produzione. Offre un ottimo equilibrio tra qualità, VRAM e velocità. Passare a Q8 solo se si osservano degradazioni qualitative specifiche sul proprio caso d'uso dopo test. FP16 solo per fine-tuning o ricerca.

Dove trovare i modelli quantizzati

Hugging Face è il repository principale per i modelli open source, incluse le versioni quantizzate. Per i modelli GGUF (usati con Ollama e llama.cpp), la fonte principale è il profilo bartowski su Hugging Face, che produce quantizzazioni di alta qualità per tutti i modelli principali. Per AWQ, molti provider rilasciano versioni ufficiali.

I nomi dei file includono la specifica di quantizzazione: Llama-3.3-70B-Instruct-Q4_K_M.gguf indica Llama 3.3 70B Instruct, quantizzato a 4 bit con il metodo K_M (buon equilibrio qualità/velocità). Q4_K_S è più veloce ma leggermente meno preciso; Q4_K_L è più preciso ma usa più VRAM.

Cosa fa un serving framework

Un framework di serving è il software che prende il modello (i file dei pesi) e lo rende accessibile come servizio HTTP — esponendo un'API a cui le applicazioni possono fare richieste. Non è opzionale: senza un serving framework, il modello è solo un file inutilizzabile. Il framework gestisce il caricamento in VRAM, le richieste concorrenti, la gestione della memoria, la quantizzazione e l'ottimizzazione dell'inferenza.

La scelta del framework influenza significativamente le performance del sistema in produzione — la stessa GPU con lo stesso modello può produrre velocità di inferenza molto diverse a seconda del framework e della sua configurazione.

Ollama Semplicità

Il framework più semplice da installare e usare. Un singolo binario che gestisce download del modello, serving e API compatibile OpenAI. Ideale per PoC, sviluppo e deployment leggero. Non ottimizzato per produzione ad alto volume ma perfettamente adeguato per uso aziendale a basso-medio traffico (decine di utenti concorrenti).

Installazione: 1 comando API OpenAI-compatibile macOS / Linux / Windows GGUF nativo Multi-modello
Ideale per: PoC, sviluppo, team piccoli, prima installazione. Limite: throughput limitato su molti utenti concorrenti.
vLLM Produzione · High throughput

Il framework di riferimento per deployment di produzione ad alto throughput. Implementa PagedAttention — un'ottimizzazione che gestisce la memoria del contesto in modo molto più efficiente, aumentando il numero di richieste concorrenti gestibili con lo stesso hardware. API OpenAI-compatibile. Richiede GPU NVIDIA con CUDA e setup più complesso di Ollama.

PagedAttention Alta concorrenza API OpenAI-compatibile Python/CUDA Produzione enterprise
Ideale per: produzione con molti utenti, integrazione in sistemi esistenti, massimo throughput. Richiede: NVIDIA GPU, competenze DevOps.
Text Generation Inference (TGI) Produzione · Hugging Face

Il framework ufficiale di Hugging Face per serving LLM. Ottimizzato per i modelli dell'ecosistema HF, con supporto nativo per tutti i formati di quantizzazione e integrazione con l'Hub. Concorrente diretto di vLLM con caratteristiche simili. Preferito da chi è già nell'ecosistema Hugging Face e vuole integrazione nativa con i loro strumenti.

Hugging Face nativo Flash Attention 2 Docker ready Quantizzazione integrata Streaming responses
Ideale per: chi usa l'ecosistema HF, container Docker, deployment Kubernetes. Alternativa valida a vLLM.
llama.cpp CPU · Edge · GGUF

Il framework originale per running di modelli GGUF senza GPU (o con GPU consumer/Apple Silicon). Permette di girare modelli quantizzati su CPU, con performance accettabili per uso leggero. Ollama è costruito sopra llama.cpp. Rilevante per edge deployment, hardware senza GPU dedicata, o Apple MacBook/Mac Studio per sviluppo.

Il rischio interno: la superficie spesso ignorata

Il self-hosting elimina i rischi verso provider esterni. Ma un sistema LLM deployato internamente introduce una superficie di rischio interna che richiede presidio attivo. Un modello RAG con accesso a documentazione tecnica riservata è, senza controlli adeguati, un sistema che può restituire informazioni sensibili a qualsiasi utente della rete aziendale con accesso all'endpoint.

La domanda da porsi non è solo "i dati sono al sicuro dall'esterno?" ma anche "chi internamente può interrogare il sistema? Con quali dati? Con quali log?". Queste domande vanno risolte prima del go-live, non dopo.

🔐

Autenticazione e autorizzazione sull'endpoint

L'endpoint del modello (es. http://llm-server:8000/v1/chat/completions) deve essere protetto da autenticazione. Un endpoint aperto in rete aziendale è accessibile a chiunque sulla rete — inclusi dispositivi compromessi. Implementare API key per applicazioni, autenticazione SSO aziendale per utenti, e RBAC (Role-Based Access Control) per limitare l'accesso a specifici gruppi o sistemi RAG per utenti autorizzati.

Priorità Obbligatorio
🌐

Isolamento di rete del server LLM

Il server GPU non deve essere raggiungibile direttamente dalla rete aziendale generale. Deve trovarsi in un segmento di rete dedicato (VLAN o subnet isolata), accessibile solo tramite un reverse proxy o API gateway che applica autenticazione, rate limiting e logging. Il server GPU non deve avere accesso diretto a Internet.

Priorità Obbligatorio
📋

Logging delle query con policy di retention

Ogni query al modello dovrebbe essere loggata con: timestamp, utente/sistema richiedente, lunghezza del prompt (non necessariamente il contenuto), lunghezza della risposta, latenza. Se si logga il contenuto delle query (utile per debug e audit), definire una policy di retention esplicita e un accesso controllato ai log — i log di query contengono i dati inviati al modello.

Priorità Alta
📊

Monitoring e alerting

Monitorare utilizzo del sistema (query/minuto, latenza, errori) e definire alert per pattern anomali: picchi di volume insoliti, query molto lunghe (possibile estrazione dati), errori ripetuti (possibile attacco). Il monitoring non è solo operativo — è anche uno strumento di sicurezza. Strumenti: Prometheus + Grafana per metriche, qualsiasi SIEM aziendale per eventi di sicurezza.

Priorità Alta
🤖

Protezione del modello e dei pesi

I file dei pesi del modello (decine o centinaia di GB) sono asset aziendali — specie se su un modello fine-tuned su dati proprietari. Devono essere trattati come qualsiasi altro asset IT critico: backup regolari, controllo degli accessi al filesystem, cifratura a riposo. Un modello fine-tuned su dati aziendali perso o sottratto rappresenta una perdita di investimento e potenzialmente un rischio di esposizione indiretta di know-how.

Priorità Media
💉

Prompt injection nei sistemi RAG

Se il sistema RAG processa documenti di terzi o input non controllati (email, documenti caricati dagli utenti), esiste il rischio di prompt injection: un testo malevolo nel documento può tentare di manipolare le istruzioni del modello. Sanitizzare gli input provenienti da fonti non fidate, definire system prompt che limitano il comportamento del modello, e non dare al modello accesso a strumenti o sistemi che non dovrebbe usare.

Priorità Alta (per RAG)
