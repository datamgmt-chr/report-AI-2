Sezione 01

Avviare il training via API — senza infrastruttura propria

I vendor principali (OpenAI, Anthropic, Google) offrono API di fine-tuning che non richiedono GPU proprie né infrastruttura ML. Il processo è accessibile — la complessità è nel dataset, non nel training stesso.

Cinque anni fa il fine-tuning richiedeva cluster GPU, competenze di MLOps, e settimane di lavoro di engineering. Oggi, per i casi d'uso più comuni (tipo 1 e tipo 2), è un processo in pochi passi via API. La democratizzazione dell'accesso ha abbassato drasticamente la barriera tecnica — spostando il problema dalla complessità dell'infrastruttura alla qualità dei dati.

1
Fase 1
Prepara e carica il dataset
Il dataset validato nel Report B (formato JSONL, check di qualità superati, validation set separato) viene caricato sul server del vendor tramite API. Salva sempre il job ID restituito dall'API — serve per monitorare il training e recuperare il modello.
# Esempio pseudocodice — caricamento dataset upload_response = client.files.upload( file="dataset_training.jsonl", purpose="fine-tune" ) file_id = upload_response.id # salva questo
2
Fase 2
Configura i parametri del training
I parametri chiave da impostare: il modello base (scegli il più capace che hai i dati per giustificare), gli epochs (numero di passaggi sull'intero dataset — troppo pochi: underfitting, troppi: overfitting), il learning rate multiplier (default del vendor è quasi sempre il punto di partenza giusto per il primo round).

Regola pratica per gli epochs: 2–4 epoch per dataset fino a 200 esempi, 1–2 epoch per dataset più grandi. Più epochs aumentano il rischio di overfitting su dataset piccoli — il modello memorizza gli esempi invece di generalizzare il pattern.
job = client.fine_tuning.jobs.create( training_file=file_id, validation_file=validation_file_id, # sempre model="base-model-name", hyperparameters={ "n_epochs": 3, # punto di partenza "learning_rate_multiplier": "auto" } )
3
Fase 3
Monitora il job e recupera il modello
Il training richiede tipicamente 15–60 minuti per dataset di 100–500 esempi. L'API fornisce eventi di aggiornamento con le metriche di training. Il modello fine-tuned viene identificato da un model ID unico — da usare nelle chiamate API esattamente come si usa il modello base.
# Controlla lo stato del job status = client.fine_tuning.jobs.retrieve(job.id) model_id = status.fine_tuned_model # disponibile quando status="succeeded" # Usa il modello fine-tuned response = client.chat.completions.create( model=model_id, # sostituisce il modello base messages=[...] )
Sezione 02

Monitorare il training — leggere la loss curve

La loss curve è il segnale principale durante il training. Sa dirti se il modello sta imparando, se sta memorizzando, o se c'è un problema con il dataset. Imparare a leggerla è la differenza tra un training produttivo e uno da rifare.

Linea guida 01
01
Ferma il training quando la validation loss smette di scendere — non quando gli epoch finiscono
Il numero di epoch configurato è un limite superiore — il punto ottimale è dove la validation loss è al minimo
★★★
Impatto
I tre scenari e cosa fare

Training e validation loss scendono insieme (scenario buono): il modello sta imparando il pattern senza memorizzare. Continua fino a plateau o convergenza. Il modello finale è quello dell'ultimo step.

Training scende, validation risale (overfitting): il modello ha memorizzato gli esempi del training set ma non ha generalizzato. Il punto ottimale era il momento prima che la validation cominciasse a risalire. Soluzioni: ridurre gli epoch, aumentare la dimensione del dataset, o aumentare la diversità degli esempi.

Entrambe le loss piatte (non impara): il modello non sta apprendendo nulla di utile. Cause più comuni: learning rate troppo basso (usa "auto"), dataset con label noise o formato scorretto, dataset troppo piccolo per il task. Controlla prima il formato degli esempi.

Sezione 03

Valutare il modello fine-tuned — con attenzione alle regressioni

La valutazione post fine-tuning non misura solo se il modello ha migliorato sul task target — misura anche se ha peggiorato su tutto il resto. Le regressioni su task non ottimizzati sono il rischio specifico del fine-tuning che la valutazione deve sempre coprire.

La valutazione del modello fine-tuned segue la stessa metodologia del Report B della Leva 2 (golden dataset, metriche specifiche per il task, LLM-as-judge dove necessario). Ma ha un componente aggiuntivo critico: il test di regressione. Un modello che migliora del 20% sul task ottimizzato ma peggiora del 30% su task non ottimizzati è un modello da non deployare.

Confronta con il modello base sugli stessi casi. Degradamento accettabile: ≤ 10% rispetto al baseline. Sopra il 20% è un segnale di problema.

Il fine-tuning può rendere il modello meno robusto su questi casi. Comportamento almeno equivalente al baseline. Il fine-tuning non deve ridurre la robustezza.
Istruzioni nel system prompt Il fine-tuning può ridurre la capacità del modello di seguire istruzioni diverse da quelle viste nel training Testa il modello con system prompt diversi da quello usato nel dataset di training. Verifica che rispetti comunque le istruzioni nuove. Il modello deve seguire le istruzioni del system prompt anche se diverse dal training. Degradamento preoccupante se il modello "ignora" nuove istruzioni.
Output strutturato su schemi nuovi Il fine-tuning su uno schema specifico può rendere il modello meno flessibile con schemi diversi Testa con schemi JSON diversi da quelli del dataset di training. Il tasso di JSON valido non deve essere peggiorato rispetto al baseline. JSON validity rate ≥ baseline su schemi non visti nel training.
La regola del "beneficio netto"

La decisione di deployare il modello fine-tuned si basa sul beneficio netto: il miglioramento sul task target pesa abbastanza da giustificare i degradamenti su altri task? Non esiste una risposta universale — dipende da quanto i vari task sono usati nel sistema reale. Un degradamento del 15% su task che rappresentano l'1% del traffico è molto meno grave di un degradamento del 5% su task che rappresentano il 40% del traffico. Calcola il beneficio netto sulla distribuzione reale del traffico.

Sezione 04

Il ciclo iterativo — quando il primo round non basta

Il fine-tuning raramente converge al risultato ottimale al primo round. Il ciclo iterativo è la strategia per migliorare progressivamente senza sprecare risorse su training che non producono miglioramenti.

Round 1 — Baseline fine-tuned
Train → Valuta → Diagnostica
Primo round con 50–100 esempi di alta qualità. Obiettivo: capire dove il modello migliora e dove ancora sbaglia — non ottenere il risultato finale. Non aggiungere esempi prima di aver analizzato i risultati del round 1.
Output atteso: una lista delle categorie di errori che il modello fa ancora — ordinata per frequenza e impatto.
Round 2 — Mirato sui gap
Aggiungi esempi mirati → Ri-train
Aggiungi esempi specificamente nelle categorie dove il round 1 ha mostrato problemi. Non aggiungere esempi uniformemente — aggiungi dove il modello sbaglia ancora. 30–50 nuovi esempi mirati spesso producono più miglioramento di 200 esempi generici.
Criterio di aggiunta: per ogni categoria di errore del round 1, aggiungi 10–20 esempi che coprono esattamente quel tipo di caso.
Round 3+ — Convergenza
Ripeti finché il miglioramento si stabilizza
Il miglioramento per round diminuisce progressivamente. Fermati quando il miglioramento sul golden dataset scende sotto una soglia minima significativa — tipicamente quando un nuovo round produce meno del 2–3% di miglioramento sulla metrica target.
Segnale di stop: il round N+1 non produce miglioramento misurabile rispetto al round N. Il problema non è il dataset — è il limite del tipo di fine-tuning scelto.
Quando smettere di iterare
Se dopo 3 round di fine-tuning con dataset di qualità il modello non raggiunge la soglia di qualità target, il problema non è nel processo — è nella scelta dello strumento.
Tre scenari in cui smettere di iterare: 1) Il miglioramento si è stabilizzato sopra la soglia accettabile — il fine-tuning ha funzionato, deployare. 2) Il miglioramento si è stabilizzato sotto la soglia — il task richiede capacità che il modello base non ha, considera un modello base più capace (Leva 2) o un tipo di fine-tuning diverso. 3) Il miglioramento sul task target produce regressioni inaccettabili — il task e il dominio sono troppo diversi dal training generale del modello base, riconsiderare l'approccio.

I principi che attraversano tutta la serie
Ogni leva è uno strumento con un caso d'uso preciso. La competenza non è sapere come funziona ogni strumento — è sapere quale scegliere per quale problema, nell'ordine giusto.
1. L'ordine delle leve è una gerarchia di costo e reversibilità. Il prompt engineering si cambia in un'ora. Il RAG in un giorno. Il fine-tuning in settimane. Investi sempre nella leva meno costosa che risolve il problema — non in quella più sofisticata.

2. La qualità dei dati precede la qualità dell'algoritmo. Vale per il RAG (la qualità del corpus), per il fine-tuning (la qualità del dataset), per l'orchestrazione (la qualità dello stato). Nessun algoritmo recupera dati sbagliati.

3. La semplicità è un valore, non un compromesso. Un agente singolo ben configurato batte quasi sempre un sistema multi-agente mal progettato. Un prompt chiaro batte quasi sempre un sistema RAG mal indicizzato. La complessità aggiuntiva deve comprare qualcosa di misurabile.

4. La valutazione non è opzionale. Ogni leva produce un sistema da valutare — sul proprio task, con le proprie metriche, sulla propria distribuzione reale. I benchmark generici e le demo convincenti non predicono le prestazioni in produzione.

5. I sistemi evolvono — e devono essere progettati per evolversi. I modelli cambiano, i dati cambiano, i requisiti cambiano. Un sistema di agenti AI è un sistema vivo che richiede manutenzione continua. La documentazione delle decisioni, i golden dataset, e le pipeline di valutazione non sono overhead — sono ciò che rende il sistema mantenibile nel tempo.
