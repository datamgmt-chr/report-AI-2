Categoria 04

Esecuzione di codice

Tool che eseguono logica arbitraria generata dall'LLM in un processo separato. La categoria più flessibile — il contenuto del tool call non è noto a design time. Il sandbox è il confine di sicurezza, e il ciclo errore→correzione è parte normale del flusso.

⚙️
Esecuzione di codice
Python, SQL, bash · Logica arbitraria · Il sandbox isola dall'host
execute_python · run_sql · execute_code · run_script
Esecuzione di codice generato dall'LLM in un ambiente isolato — calcoli, analisi dati, trasformazioni, generazione artefatti
Sandbox obbligatorio No approv. tipicamente Ciclo errore→fix
Pattern di naming — cosa segnala il nome

Il nome deve includere il linguaggio — non solo "execute" generico. L'LLM usa il nome per capire quale ambiente ha a disposizione.

execute_python run_sql run_bash execute_r_script

❌ Evita: execute_code senza linguaggio — l'LLM non sa cosa può scrivere. Ogni linguaggio ha un tool separato con la propria description dell'ambiente.

Approvazione — quando sì e quando no

Tipicamente no: calcoli, analisi, trasformazioni dati. Il codice viene generato dall'LLM, eseguito nel sandbox, e il risultato è testo — nessun side effect sul sistema host.

Sì quando: il codice prodotto potrebbe modificare file persistenti, inviare richieste HTTP, o accedere a risorse esterne. In questi casi mostra il codice prima di eseguirlo — specialmente se l'utente non ha visto cosa verrà eseguito.

Regola pratica: se il sandbox è correttamente isolato (no rete, no filesystem host), non serve approvazione. L'isolamento è il guardrail, non il HITL.

Output contract — cosa deve tornare all'LLM

Successo: stdout completo. Non filtrare — il modello decide cosa è rilevante nel contesto della risposta.

Errore: traceback completo con la riga incriminata. Il modello ha bisogno dell'errore esatto per correggere — non un messaggio abbreviato.

Artefatti (file, plot): path del file prodotto come stringa nel risultato: "PLOT SALVATO: /tmp/chart.png". Il runtime poi decide come gestire il file.

Output vuoto: se il codice non stampa nulla, restituire "[Esecuzione completata senza output]" — non stringa vuota.

Errori tipici di design
✗Ambiente non descritto: la description non dice quali librerie sono disponibili. Il modello genera import che falliscono. Fix: elenco esplicito di librerie nella description.
✗Errore non reiniettato: il runtime cattura l'errore ma restituisce un messaggio generico invece del traceback. Il modello non può correggersi. Fix: sempre il traceback completo come tool_result.
✗Nessun timeout: il codice entra in loop infinito, il processo non termina mai. Fix: timeout obbligatorio (30s), configurato nel subprocess, dichiarato nella description.
✗Stesso processo host: il codice gira con exec() inline invece di un subprocess. Un errore nel codice generato crasha l'intero agente. Fix: sempre subprocess o container separato.

Il design critico per run_sql — separare la lettura dalla scrittura

Non esporre un unico tool SQL generico che può fare tutto. Esponi due tool separati: query_database (solo SELECT, read-only) e execute_sql (INSERT/UPDATE/DELETE, con approvazione obbligatoria). In questo modo l'LLM usa il tool read-only per esplorare i dati — che è il 90% dei casi d'uso — e il tool di scrittura solo quando esplicitamente necessario, con un guardrail automatico.

Nella description di query_database: "Solo query SELECT. Per modificare dati usa execute_sql (richiede approvazione dell'utente)." Questo rende la separazione esplicita all'LLM invece di affidarsi al fatto che "non gli viene in mente" di fare UPDATE.

Categoria 05

Integrazione con sistemi esterni

Tool che si connettono a sistemi terzi — CRM, project management, calendari, repository di codice, servizi cloud. Il principio guida è sempre lo stesso: esponi intenzioni semantiche, nascondi la complessità tecnica dell'integrazione.

🔌
Sistemi esterni
CRM, GitHub, calendari, Slack, cloud · Wrapper semantici · MCP dove disponibile
Sistemi comuni: CRM · GitHub · Calendar · Slack · Cloud storage
Ogni sistema espone decine di endpoint — l'agente deve vederne solo 3–6 semanticamente significativi per il suo caso d'uso
Wrapper semantici MCP se disponibile Rischio per sistema
Pattern di naming per sistemi esterni

Non includere il nome del sistema nel tool — esponi l'intenzione. L'LLM non deve sapere che stai usando Salesforce: deve sapere che può "trovare un cliente".

get_customer_info create_support_ticket get_open_issues schedule_meeting post_to_channel

❌ Evita nomi tecnici: salesforce_query, github_api_call, gcal_insert_event. Il modello invocherà questi tool meno spesso e con parametri sbagliati perché non capisce l'intenzione.

Quanti tool esporre per sistema

Regola pratica: 3–6 tool per sistema, corrispondenti alle operazioni reali del caso d'uso dell'agente — non all'intera superficie API del sistema.

Esempio per un agente di supporto con Salesforce: get_customer_info, get_open_tickets, create_ticket, update_ticket_status, get_order_history. Cinque tool — non i 200 endpoint disponibili nell'API Salesforce.

Se servono più di 6 tool da uno stesso sistema, probabilmente l'agente sta cercando di fare troppo — valuta di suddividerlo in agenti specializzati.

MCP vs. wrapper manuale — come scegliere

Usa MCP quando: esiste già un server MCP per il sistema (Salesforce, GitHub, Google Drive, filesystem). Risparmia il lavoro di costruire il wrapper e gestisce autenticazione e schema automaticamente.

Scrivi un wrapper manuale quando: il sistema non ha un server MCP, hai bisogno di tool con logica custom (es. get_customer_info che unisce dati da tre endpoint diversi), o vuoi controllare esattamente cosa esponi all'LLM.

Ibrido: usa MCP per la connessione di base ma wrappa i tool MCP in funzioni Python che normalizzano l'output e aggiungono la logica di business necessaria.

Errori tipici
✗Autenticazione nel prompt: credenziali o token passati nel system prompt o nella description. Fix: sempre in env variables nel codice del wrapper — mai visibili all'LLM.
✗Output con ID tecnici: il tool restituisce l'ID interno di Salesforce invece del nome del cliente. Il modello usa l'ID nella risposta all'utente. Fix: output con nomi leggibili, ID solo dove serve per follow-up call.
✗Rate limit non gestito: il wrapper non gestisce 429/rate limit e restituisce l'errore HTTP all'LLM raw. Fix: retry con backoff nel wrapper, messaggio semantico al fallimento: "Sistema temporaneamente non disponibile, riprova tra 30s."
Categoria 06

Elaborazione file e media

Tool che leggono, trasformano o producono file — PDF, immagini, CSV, documenti Word. Il pattern caratteristico: l'input e l'output sono artefatti su disco, non testo nel context window. La gestione dei path è parte del design.

📄
Elaborazione file e media
PDF, immagini, CSV, documenti · Input/output sono artefatti · Path nel context
parse_pdf · extract_text · convert_format · generate_report · resize_image · merge_documents
Lettura, trasformazione e produzione di file — il tool opera su percorsi di file, non su contenuto inline
Spesso reversibile No approv. tipicamente Path management critico
Pattern di naming — verbo + formato

Il formato deve essere nel nome — segnala all'LLM per quale tipo di file usare il tool.

parse_pdf extract_text_from_image convert_csv_to_excel generate_pdf_report merge_pdfs

❌ Evita: process_file, handle_document — troppo generici. Un tool per formato, o almeno un tool per famiglia di formati.

Il problema dei path — come gestirlo

I tool di file operano su path nel filesystem. L'LLM non sa dove sono i file — deve essere informato esplicitamente nel messaggio utente o nel context.

Pattern corretto: quando l'utente carica un file, il runtime lo salva in una directory accessibile al tool (es. /data/uploads/) e aggiunge al messaggio: "File caricato: /data/uploads/contratto.pdf". L'LLM usa questo path nel parametro del tool.

Output path: i file prodotti dal tool (report, conversioni) vengono salvati in una directory di output e il path viene restituito come stringa nel risultato: "Report salvato: /data/outputs/report_2026.pdf".

Output contract per i tool di file

Tool di lettura (parse_*, extract_*): il contenuto estratto come testo nel tool_result — l'LLM poi lo elabora. Se il file è troppo grande per il context, restituisci un summary + path per accesso successivo.

Tool di trasformazione (convert_*, merge_*): path del file prodotto come stringa. Non restituire il contenuto del file — solo il path. L'LLM non ha bisogno di leggere il CSV prodotto per confermare che è stato creato.

Errori su file: messaggi semantici invece di eccezioni tecniche: "File non trovato: controlla che il path sia corretto" invece di FileNotFoundError: [Errno 2].

Errori tipici
✗Contenuto nel context invece del path: il tool restituisce tutto il testo del PDF come tool_result. Satura il context window. Fix: per file grandi, restituisci abstract + path; per file piccoli, il testo va bene.
✗Path hardcoded nella description: la description dice "il file è in /uploads/". Se il path cambia, la description è sbagliata. Fix: il path viene sempre passato come parametro — mai come default implicito.
✗Formato non verificato: il tool prova a parsare un PNG come PDF. Fix: verifica l'estensione del file nel wrapper Python prima di processarlo, con messaggio di errore semantico.

parse_pdf — template con gestione path
Cosa fa: Estrae il testo da un file PDF e lo restituisce come testo strutturato con indicazione delle sezioni principali. Il principio unificante
Ogni categoria ha un rischio specifico e un'istruzione chiave che lo mitiga. Progettare un tool senza identificare prima il suo rischio specifico è progettare al buio.
La tassonomia non è rigida — un tool reale può attraversare più categorie (es. generate_and_send_report tocca esecuzione codice, file e comunicazione). In questi casi si applicano le regole della categoria più rischiosa: reversibilità della comunicazione, approvazione sempre, pattern mostra-poi-invia. Il tool composito eredita sempre il profilo di rischio più alto tra le categorie che tocca.
