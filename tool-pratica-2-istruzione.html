Sezione 01

La mappa — ogni istruzione ha un posto preciso

Le istruzioni su come usare i tool si distribuiscono in tre luoghi distinti, ognuno con uno scopo diverso. Mettere le istruzioni nel posto sbagliato funziona a volte — ma produce sistemi fragili e comportamento incoerente.

La regola della ridondanza deliberata
I guardrail critici vanno in entrambi i posti: nella description del tool ("NON inviare a destinatari esterni") e nel system prompt ("Prima di inviare qualsiasi email, mostra il destinatario e il contenuto e attendi conferma"). La ridondanza è deliberata — non fastidiosa.
Lo schema del tool viene letto quando il modello considera quale tool usare. Il system prompt viene letto ad ogni generazione. Un guardrail solo nello schema può essere ignorato se il modello non lo consulta esplicitamente — un guardrail nel system prompt è sempre presente nel context. Per le azioni irreversibili, non scegliere: usali entrambi.
Sezione 02

Scrivere description che guidano davvero il comportamento

La description del tool è il campo più critico dell'intero sistema di istruzioni. Non è documentazione — è l'istruzione che l'LLM legge per decidere se e come usare quel tool. Una description vaga produce invocazioni sbagliate.

Linea guida 01
01
Ogni description risponde a tre domande: cosa fa, quando usarlo, quando NON usarlo
La terza domanda è la più trascurata — e quella che previene gli usi sbagliati più costosi
★★★
Critico
Description vaga vs. description operativa — confronto diretto
❌ Vaga — l'LLM interpreta come vuole
"name": "send_email", "description": "Invia un'email." → L'LLM non sa: - A chi può inviare - Quando deve farlo vs. mostrare bozza - Se serve conferma prima - Cosa mettere nell'oggetto → Invierà quando decide lui, a chi decide lui
✓ Operativa — guida il comportamento
"name": "send_email", "description": "Invia un'email al destinatario specificato. USARE quando: l'utente ha approvato esplicitamente il contenuto e il destinatario. NON USARE: se il destinatario non è stato confermato dall'utente, o se il contenuto contiene dati sensibili non approvati. PRIMA DI USARE: mostra sempre bozza con oggetto e destinatario."
La struttura completa di una description ben scritta
Anatomia — description operativa
Parte 1
Cosa fa
Una frase concisa che descrive l'azione prodotta. Usa un verbo d'azione concreto. Evita "permette di", "consente di" — scrivi cosa fa il tool, non cosa permette all'utente di fare.
Esempio: "Invia un'email tramite il server SMTP aziendale al destinatario specificato."
Parte 2
Quando usarlo
I trigger espliciti — le condizioni in cui questo tool è la scelta giusta. Sii specifico: "quando l'utente chiede di inviare" non è sufficiente se ci sono varianti (bozze, schedulazioni, forward). Distingui questo tool dagli altri simili disponibili.
Esempio: "Usare quando l'utente ha confermato esplicitamente il contenuto e il destinatario. Non usare per salvare bozze (usa save_draft) né per email schedulate (usa schedule_email)."
Parte 3
Quando NON usarlo
I casi di esclusione espliciti. Questa è la parte più importante per prevenire errori — un modello tende a usare il tool quando è incerto se sia opportuno. I casi di esclusione lo bloccano nei momenti ambigui.
Esempio: "NON usare se: il destinatario non è nella whitelist aziendale, il messaggio contiene dati personali non anonimi, l'utente non ha approvato esplicitamente."
Parte 4
Vincoli operativi
Limiti tecnici o di policy da rispettare: rate limit, dimensioni massime, formati accettati, ambiente disponibile. Non duplicare questi nei parametri se già nella description — scegli uno dei due posti.
Esempio: "Max 1 email per turno. Dimensione allegati: max 10MB. Solo testo plain o HTML — nessun allegato eseguibile."
Le description dei parametri — non solo il tipo
❌ Solo il tipo — l'LLM deve indovinare
"parameters": { "to": {"type": "string"}, "subject": {"type": "string"}, "body": {"type": "string"}, "cc": {"type": "array"} } → L'LLM non sa: - "to" deve essere un singolo indirizzo? - "subject" ha una lunghezza max? - "body" supporta HTML o solo plain? - "cc" è facoltativo?
✓ Con descrizione semantica — comportamento preciso
"parameters": { "to": { "type": "string", "description": "Indirizzo email del destinatario principale. Deve essere nella whitelist aziendale. Un solo indirizzo per chiamata." }, "subject": { "type": "string", "description": "Oggetto email. Max 100 caratteri. Non usare maiuscole eccessive." }, "body": { "type": "string", "description": "Corpo in HTML o plain text. Usa \\n per newline in plain." }, "cc": { "type": "array", "description": "Facoltativo. Max 5 indirizzi. Tutti nella whitelist." } }
Sezione 03

Istruire su tool esterni — API, database, sistemi specifici

Quando il tool wrappa un sistema esterno complesso (un CRM, un gestionale, un'API con decine di endpoint), il problema è filtrare: quali funzionalità esporre all'LLM, come mappare il "mondo dell'LLM" sul "mondo del sistema", e come gestire la complessità del sistema senza sommergere il modello.

Linea guida 02
02
Esponi funzioni ad alto livello — non endpoint di API raw
L'LLM opera meglio su tool che corrispondono a intenzioni, non a operazioni tecniche di basso livello
★★★
Impatto
Esempio: wrappare Salesforce per un agente di supporto
❌ Esporre gli endpoint raw — troppa complessità
tools = [ "salesforce_query", # SOQL generico "salesforce_create", # POST su qualsiasi oggetto "salesforce_update", # PATCH su qualsiasi record "salesforce_delete", # DELETE su qualsiasi record "salesforce_describe", # schema degli oggetti ] → L'LLM deve conoscere SOQL, i nomi degli oggetti Salesforce (Account, Contact, Opportunity...), i field name esatti. → 1 tool generico = 100 modi di usarlo sbagliato.
✓ Tool semantici specifici del caso d'uso
tools = [ "get_customer_info", # cerca per nome/email/tel "get_open_tickets", # ticket aperti per customer "create_support_ticket", # crea ticket con categoria "update_ticket_status", # aggiorna stato ticket "get_order_history", # storico ordini cliente ] → Ogni tool ha un'intenzione chiara. → Il runtime traduce internamente in chiamate SOQL corrette. → L'LLM non ha bisogno di conoscere il modello dati di Salesforce.
Come istruire su un tool esterno con molte funzionalità — il pattern "wrapper semantico"

Il pattern è: scrivi una funzione Python per ogni intenzione dell'agente (non per ogni endpoint dell'API), dagli un nome che corrisponde a quell'intenzione, e nascondi la complessità tecnica dentro la funzione.

Wrapper semantico — da API raw a tool intelligente
# ── Il tool come l'LLM lo vede (schema semplice) ───────────────────── { "name": "get_customer_info", "description": "Recupera le informazioni di un cliente. Usare quando l'utente menziona il nome, email o numero di telefono di un cliente e ha bisogno di dati del suo profilo. NON usare per cercare ordini o ticket (usa get_order_history o get_open_tickets).", "input_schema": { "properties": { "search_term": { "type": "string", "description": "Nome, email o telefono del cliente." } }, "required": ["search_term"] } } # ── L'implementazione che il runtime chiama (nascosta all'LLM) ──────── def get_customer_info(search_term: str) -> dict: # Qui c'è tutta la complessità: autenticazione, SOQL, gestione errori sf = Salesforce(username=os.getenv("SF_USER"), ...) # Cerca su più campi — l'LLM non sa che esistono questi field name soql = f""" SELECT Id, Name, Email, Phone, Account.Name FROM Contact WHERE Name LIKE '%{search_term}%' OR Email = '{search_term}' OR Phone = '{search_term}' LIMIT 5 """ results = sf.query(soql) if not results["records"]: return {"found": False, "message": "Nessun cliente trovato."} # Restituisce struttura pulita — nessun ID interno, nessun campo tecnico return { "found": True, "customers": [{ "name": r["Name"], "email": r["Email"], "phone": r["Phone"], "company": r["Account"]["Name"] if r["Account"] else None } for r in results["records"]] }
L'output del tool — pulito e denso di significato

Il risultato restituito dal tool diventa tool_result nel context window dell'LLM. L'LLM legge questo testo per produrre la risposta successiva — un output verboso e pieno di campi tecnici (ID interni, timestamp in epoch, codici di stato HTTP) degrada la qualità della risposta. Restituisci solo i dati semanticamente rilevanti, in un formato che un umano capirebbe.

Regola pratica: rimuovi ID interni, converti timestamp in date leggibili, usa nomi di campo descrittivi, e includi un campo message esplicito quando il risultato è vuoto — il modello gestisce meglio "Nessun ticket aperto" di un array vuoto.

Sezione 04

Istruire un agente che esegue codice Python

L'agente data analyst: come si configura il system prompt, come si descrive l'ambiente, come si gestisce il ciclo errore→correzione, e come si passa un file/dataset all'agente.

L'agente che genera ed esegue codice ha peculiarità specifiche rispetto all'agente che usa API: il codice generato non è noto a design time, l'ambiente di esecuzione deve essere esplicitamente descritto, e il ciclo di errore-correzione è parte normale del flusso — non un caso eccezionale da gestire.

Linea guida 03
03
Descrivi l'ambiente nella description del tool, non nel system prompt
L'LLM deve sapere cosa può usare al momento di generare il codice — non prima, in modo generico
★★★
Impatto
System prompt + tool schema per un agente data analyst
System prompt — agente data analyst
# SYSTEM PROMPT ─────────────────────────────────────────────────────── """ Sei un assistente di analisi dati. Quando ricevi dati o dataset, usa il tool execute_python per analizzarli. APPROCCIO STANDARD: 1. Prima esplora i dati (shape, dtypes, .head(), .describe()) 2. Poi esegui l'analisi richiesta 3. Usa print() per ogni risultato intermedio che vuoi mostrare 4. Se il codice produce un errore, leggilo e correggi — non chiedere all'utente di farlo STILE DI OUTPUT: - Numeri: formatta con separatori di migliaia e 2 decimali dove utile - Tabelle: usa tabulate(df, headers='keys', tablefmt='simple') - Non stampare DataFrames raw (troppo verbosi) — usa .to_string() o seleziona le colonne rilevanti LIMITI: - Max 3 tentativi per correggere lo stesso errore — poi segnala - Se un calcolo richiede dati che non hai, chiedi all'utente invece di inventarli """ # SCHEMA DEL TOOL execute_python ────────────────────────────────────── { "name": "execute_python", "description": "Esegue codice Python in un ambiente isolato. LIBRERIE DISPONIBILI: pandas, numpy, matplotlib, seaborn, scipy, sklearn, tabulate. NON disponibili: requests, openai, boto3, db libs. FILESYSTEM: puoi leggere file da /data/ (es. /data/dataset.csv). Non puoi scrivere file — usa print() per l'output. OUTPUT: tutto ciò che viene stampato con print() è il risultato. Matplotlib: usa plt.savefig('/tmp/plot.png') poi print('PLOT:/tmp/plot.png'). TIMEOUT: 30 secondi. Per operazioni lente, testa prima su un campione (df.head(1000)) poi scala.", "input_schema": { "properties": { "code": { "type": "string", "description": "Codice Python completo da eseguire. Inizia sempre con gli import necessari." } }, "required": ["code"] } }
Come passare un dataset all'agente — il file nel context

Quando l'utente carica un file CSV, il modo corretto di passarlo all'agente è salvarlo nel filesystem accessibile al sandbox e informare l'LLM del path — non incorporare i dati raw nel prompt (che saturerebbe il context window).

Gestione upload file — salva nel sandbox, informa l'LLM
import shutil, uuid, os def handle_file_upload(uploaded_file, sandbox_data_dir: str = "/data"): # 1. Salva il file in una posizione accessibile al sandbox file_id = str(uuid.uuid4())[:8] safe_name = f"upload_{file_id}_{uploaded_file.filename}" dest_path = os.path.join(sandbox_data_dir, safe_name) shutil.copy(uploaded_file.path, dest_path) # 2. Costruisci il messaggio che informa l'LLM del file disponibile return { "role": "user", "content": f"""Ho caricato un file: {uploaded_file.filename} Path nel sandbox: /data/{safe_name} Dimensione: {uploaded_file.size:,} byte {user_message}""" } # L'LLM riceve il messaggio e sa che può fare: # import pandas as pd # df = pd.read_csv('/data/upload_a3f2_sales.csv') # — invece di ricevere i dati raw nel prompt
Il ciclo errore→correzione — è normale, non gestirlo come eccezione

Un agente che genera codice sbaglia spesso al primo tentativo — un errore di import, un nome di colonna diverso da quello atteso, un metodo deprecato. Questo non è un failure dell'agente: è il normale processo di sviluppo. Il traceback completo deve tornare all'LLM come tool_result, e il modello deve avere l'istruzione esplicita di correggersi invece di chiedere all'utente.

Ciclo correzione automatica con contatore di tentativi
def run_agent_with_code_execution(messages, max_attempts=3): attempt_count = {} # traccia tentativi per nome-errore while True: response = client.messages.create( model="claude-sonnet-4-5", system=system_prompt, messages=messages, tools=tools ) if response.stop_reason == "end_turn": return response # risposta finale, esci dal loop if response.stop_reason == "tool_use": tool_block = next(b for b in response.content if b.type == "tool_use") if tool_block.name == "execute_python": result = execute_python_sandbox(tool_block.input["code"]) # Controlla se è un errore già visto troppe volte error_key = extract_error_type(result) # es. "NameError", "ImportError" if error_key: attempt_count[error_key] = attempt_count.get(error_key, 0) + 1 if attempt_count[error_key] >= max_attempts: result += f"\n\n[SISTEMA: {max_attempts} tentativi falliti su questo errore. Segnala il problema all'utente.]" # Reinietta risultato (o errore) — il modello decide il passo successivo messages = messages + [ {"role": "assistant", "content": response.content}, {"role": "user", "content": [{ "type": "tool_result", "tool_use_id": tool_block.id, "content": result }]} ]
Sezione 05

Skill composte — sequenze che l'agente esegue autonomamente

Una skill composta è una sequenza di passi che l'agente deve saper eseguire in modo coordinato quando riconosce il contesto giusto — senza che ogni passo venga richiesto esplicitamente dall'utente. Va codificata nel system prompt come pattern d'azione.

Le skill composte sono il ponte tra "l'agente usa tool singoli quando richiesto" e "l'agente sa come fare X" — dove X è un compito multi-step che richiede di coordinare tool diversi in sequenza. Non sono hard-coded nel codice applicativo: sono istruzioni nel system prompt che descrivono la sequenza che l'LLM deve seguire autonomamente quando riconosce il trigger.

Linea guida 04
04
Una skill composta ha trigger, sequenza obbligatoria e criteri di completamento — tutto nel system prompt
Senza i criteri di completamento, l'agente non sa quando ha finito — e continua a iterare
★★★
Impatto
Esempio completo — skill "analisi e report contratto"
System prompt — skill composta per analisi contrattuale
""" SKILL: ANALISI CONTRATTO TRIGGER: Quando l'utente carica un documento contrattuale o chiede di "analizzare" / "revisionare" / "controllare" un contratto. SEQUENZA OBBLIGATORIA — esegui questi passi nell'ordine, senza chiedere conferma tra uno e l'altro: Passo 1 — ESTRAZIONE Usa extract_text() sul documento per ottenere il testo grezzo. Se extract_text() fallisce, usa execute_python con pdfplumber. Passo 2 — ANALISI STRUTTURATA Usa execute_python per analizzare il testo estratto. Il codice deve produrre un dict con: - parties: lista delle parti contraenti - value: valore economico (float, 0 se non presente) - duration_months: durata in mesi (int) - key_clauses: lista di {title, summary, risk_level} - non_standard: lista di clausole insolite con motivazione Passo 3 — RISK SCORE Calcola il risk score complessivo sulla base di: - Clausole non standard (peso 40%) - Valore economico relativo al settore (peso 30%) - Durata e condizioni di uscita (peso 30%) Classifica: BASSO / MEDIO / ALTO / CRITICO Passo 4 — REPORT FINALE Produci il report in formato markdown con sezioni: ## Sintesi esecutiva (3-5 righe) ## Parti e oggetto ## Analisi clausole chiave ## Elementi non standard ## Risk score: [LIVELLO] — motivazione CRITERI DI COMPLETAMENTO: - Il report è completo quando tutte e 4 le sezioni sono presenti - NON chiedere all'utente conferma tra i passi - SE un passo fallisce: riprova una volta, poi segnala il problema e procedi con i dati disponibili (non bloccare l'intera analisi) """
Il confine tra skill nel prompt e tool esplicito — quando scegliere cosa

Skill nel prompt (sequenza latente): quando la sequenza è un pattern che l'agente deve riconoscere e applicare autonomamente in base al contesto — non una funzione richiamabile dall'esterno. La logica vive nel comportamento dell'agente, non nell'architettura del sistema.

Tool esplicito: quando la sequenza deve essere invocabile in modo programmatico, riusabile da più agenti, o testa in isolamento. Si implementa come funzione Python nel runtime che orchestra i passi internamente — l'LLM vede solo il tool di alto livello (analyze_contract), non i passi interni.

La regola pratica: se la sequenza cambia in base al contesto (l'agente deve adattarla), usala come skill nel prompt. Se la sequenza è sempre identica e deve essere affidabile e testabile, wrappala in un tool esplicito che la esegue deterministicamente.

Skill nel prompt — adattiva al contesto
SKILL: RICERCA INFORMAZIONI CLIENTE Trigger: quando l'utente menziona un cliente per nome o codice. Sequenza: 1. search_crm(nome o codice) 2. Se non trovato: search_email(nome) 3. Se trovato: get_recent_interactions() 4. Sintetizza in risposta → L'agente adatta la sequenza: salta il passo 2 se il CRM ha già trovato il cliente, o aggiunge passi se il contesto lo richiede.
Tool esplicito — sempre identico e testabile
Tool: onboard_new_customer Description: "Esegue l'onboarding completo di un nuovo cliente: crea account CRM, invia email di benvenuto, crea ticket di setup, assegna account manager." → La sequenza interna è fissa nel codice Python del tool. → Il runtime la esegue sempre nello stesso modo. → Si può testare in isolamento senza coinvolgere l'LLM.
Checklist — agente con tool e skill configurato correttamente
1
Schema del tool: ogni tool ha description con cosa-fa / quando-usarlo / quando-NON-usarlo, parametri con descrizione semantica (non solo il tipo), e output contract definito.
2
System prompt: include gerarchia tra tool sovrapposti, guardrail critici ridondanti rispetto allo schema, e le skill composte con trigger, sequenza e criteri di completamento.
3
Wrapper semantici: i tool esposti all'LLM corrispondono a intenzioni (get_customer_info), non a endpoint tecnici (salesforce_query). La complessità tecnica è nascosta nell'implementazione Python.
4
Output pulito: i tool restituiscono dati semanticamente rilevanti in formato leggibile — nessun ID interno, nessun campo tecnico, messaggio esplicito per risultati vuoti.
5
Code execution configurato: la description di execute_python include librerie disponibili, filesystem accessibile e vincoli di timeout. Il ciclo errore→correzione è gestito nel runtime con un contatore di tentativi.
✓
Skill vs. tool scelto consapevolmente: le skill composte adattive vivono nel system prompt. Le sequenze fisse e testabili in isolamento sono tool espliciti nel runtime. La scelta è documentata.
