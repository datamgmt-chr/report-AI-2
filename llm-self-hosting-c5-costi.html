Il confronto corretto: TCO, non costo del modello

L'errore più comune nel valutare il self-hosting è confrontare il costo zero della licenza del modello open source con il costo per token delle API commerciali. Non è questo il confronto corretto. Il confronto corretto è tra il Total Cost of Ownership del sistema self-hosted e il costo complessivo dell'alternativa cloud — inclusi piano enterprise, integrazione e governance.

Il TCO del self-hosting ha due componenti strutturalmente diverse: costi fissi (hardware o impegno cloud, setup, personale) che esistono indipendentemente dall'uso, e costi variabili (energia, banda, storage aggiuntivo) che crescono con il volume. Questa struttura crea il fenomeno del break-even discusso nella Tab 4.

Il principio del TCO su 3 anni

Il modo corretto di confrontare le opzioni è calcolare il TCO su un orizzonte di 3 anni, includendo tutte le voci. L'on-premise ha costi iniziali molto alti che si ammortizzano nel tempo; il cloud ha costi fissi più bassi ma ricorrenti che si accumulano. Il break-even tra le due opzioni dipende dal volume d'uso e dalla configurazione specifica — la Tab 4 mostra i calcoli dettagliati.

La voce più sottostimata

In quasi tutte le valutazioni che sottostimano il costo del self-hosting, la voce mancante o minimizzata è il personale dedicato. Un sistema LLM in produzione non si gestisce da solo: richiede aggiornamenti, monitoring, troubleshooting, gestione degli accessi, test di regressione ad ogni cambio. Un MLOps senior costa €60.000–90.000/anno. Anche solo 0.3 FTE dedicati rappresentano €18.000–27.000/anno — spesso più del costo dell'hardware cloud.

Come funziona il pricing a token

I provider API addebitano in base al numero di token processati — unità di testo più piccole di una parola (mediamente ~0.75 parole per token in italiano/inglese). Il costo ha due componenti: token in input (il testo che si invia al modello, incluso il system prompt e il contesto RAG) e token in output (il testo generato dal modello). L'output costa tipicamente 2–4 volte di più dell'input.

Per dare un'idea della scala: una query tipica a un sistema RAG su documentazione tecnica potrebbe includere 500 token di system prompt, 300 token di contesto RAG recuperato, 50 token di domanda utente = 850 token input, più ~200 token di risposta output. Con GPT-4o a €2.5/M token input + €10/M token output, questa query costa circa €0.002 — due millesimi di euro. Diecimila di queste query costano €20.

Piani enterprise: struttura del costo

I piani enterprise dei principali provider non si basano sul pricing a token standard — includono componenti aggiuntive:

OpenAI Enterprise: pricing a consumo (token) con garanzie di zero data retention, DPA, SLA dedicato. Il costo per token rimane simile all'API standard ma con commitment annuale che garantisce prezzi e condizioni. Stima per uso medio (50M token/mese): €1.500–5.000/mese.

Anthropic Claude for Enterprise: struttura simile con zero retention, DPA GDPR, supporto dedicato. Pricing basato su utilizzo con sconti per commitment.

Microsoft Azure OpenAI: integra i modelli OpenAI nell'infrastruttura Azure, con i benefici del tenant Azure aziendale già esistente per molte aziende. Pricing identico all'API OpenAI ma con la governance Azure già in uso.

Come calcolare il costo API per il proprio caso

Formula base: Costo mensile = (query/mese × token_input_medi × prezzo_input) + (query/mese × token_output_medi × prezzo_output)

Valori tipici per un sistema RAG su documentazione tecnica: 800–1.500 token input (system prompt + contesto RAG + domanda), 200–400 token output. Con GPT-4o mini a €0.14/M input + €0.55/M output, 50.000 query/mese costano circa €35–70/mese — meno di €1.000/anno.

Il trend che cambia il calcolo

I prezzi API sono scesi in modo drastico negli ultimi 24 mesi. GPT-4o mini oggi costa circa 50× meno di GPT-4 due anni fa, con qualità comparabile su molti task. Questo trend sposta il break-even del self-hosting a volumi sempre più alti. Un calcolo di break-even fatto 18 mesi fa potrebbe non essere più valido oggi. Aggiornare il calcolo prima di qualsiasi decisione.

Il meccanismo del break-even

Il self-hosting ha una struttura di costo a U invertita rispetto al volume: costi fissi alti indipendentemente dall'uso, costo marginale per query quasi zero. Le API hanno il comportamento opposto: costo fisso vicino a zero, costo che cresce linearmente con il volume.

Il punto di break-even è il volume mensile di query oltre il quale il self-hosting diventa più economico. Sotto quel volume, le API costano meno. Sopra, il self-hosting ammortizza i costi fissi su abbastanza query da risultare conveniente.

Fattori che spostano il punto di break-even

Spostano il break-even verso volumi più bassi (favoriscono il self-hosting): uso di modelli API costosi (GPT-4o, Claude Sonnet), alto numero di token per query (documenti lunghi, RAG con molto contesto), uso 24/7 che massimizza l'utilizzo dell'hardware, aziende con personale IT già disponibile che assorbe il costo MLOps.

Spostano il break-even verso volumi più alti (favoriscono le API): uso di modelli API economici (GPT-4o mini, Gemini Flash), query corte con poco contesto, uso irregolare che non giustifica hardware dedicato, necessità di assumere personale MLOps dedicato.

Il break-even non è l'unico criterio

Il calcolo del break-even risponde alla domanda "quando è più economico?". Ma per molte organizzazioni la motivazione principale del self-hosting non è economica — è la sicurezza dei dati. Un'azienda che non può inviare certe informazioni fuori dal perimetro aziendale potrebbe scegliere il self-hosting anche sapendo che costerà di più. Il break-even è rilevante solo se il criterio decisionale include il costo come variabile principale.

I costi che non compaiono nel preventivo iniziale

Quasi tutte le valutazioni che sottostimano il costo del self-hosting lo fanno perché considerano solo le voci ovvie — hardware o cloud GPU, e al massimo il setup iniziale. Le voci qui elencate sono quelle sistematicamente dimenticate o minimizzate, che nella pratica rappresentano spesso il 40–60% del costo totale.

Personale specializzato continuativo

Non basta qualcuno che fa il setup iniziale. Un sistema LLM in produzione richiede manutenzione continua: aggiornamenti del framework di serving, patch di sicurezza, monitoring degli alert, test di regressione dopo ogni cambio, gestione degli accessi, troubleshooting di problemi di performance. Un MLOps part-time (0.3 FTE) in un'azienda manifatturiera media significa €18.000–27.000/anno — ogni anno, non solo anno 1.

Impatto€15k–27k/anno

Aggiornamento del modello

Come discusso nel Report C3, i modelli evolvono ogni 6–12 mesi con miglioramenti significativi. Ogni aggiornamento richiede: valutazione della nuova versione, test di regressione su tutti i casi d'uso, eventuale re-fine-tuning, migrazione graduale in produzione. Per un sistema mid-range, stimare 3–8 giorni di lavoro specializzato per ogni aggiornamento maggiore, due volte l'anno.

Impatto€3k–10k/anno

Downtime e ridondanza

Un sistema LLM senza ridondanza è un single point of failure. Se il server GPU si guasta o richiede manutenzione, il sistema non è disponibile. Per un uso produttivo che gli utenti dipendono, serve ridondanza — che significa hardware di backup o failover su cloud. Senza ridondanza, pianificare il costo di downtime accettato (stima: 2–5 ore/mese di manutenzione programmata + imprevisti).

ImpattoDowntime + €5k–20k

Costruzione e manutenzione del sistema RAG

Il modello da solo non fa quasi nulla di utile per il manifatturiero. Il valore viene dal sistema RAG che collega il modello alla documentazione aziendale. Costruire il pipeline RAG (indicizzazione documenti, vector database, retrieval, prompt engineering) richiede tipicamente 2–6 settimane di sviluppo e poi manutenzione continua: aggiornamento documenti, ottimizzazione del retrieval, gestione di documenti nuovi o modificati.

Impatto€5k–20k setup + manutenzione

Integrazione con sistemi aziendali

Connettere il sistema LLM con ERP, MES, PLM, documentale esistenti è spesso il lavoro più lungo e costoso dell'intero progetto — molto più del deploy del modello. Ogni integrazione richiede API, autenticazione, gestione degli errori, testing. Stimare 2–8 settimane di sviluppo per integrazione, a seconda della complessità del sistema target.

Impatto€5k–30k per integrazione

Formazione degli utenti e change management

Un sistema LLM usato male produce risultati peggiori di uno non usato. Gli utenti devono capire cosa il sistema sa fare, cosa non sa fare, come formulare le query, e quando non fidarsi delle risposte. Stimare 2–4 ore di formazione per utente più materiali e sessioni di Q&A ricorrenti. Per 50 utenti: 100–200 ore di formazione.

Impatto€2k–8k

Compliance, audit e documentazione

Un sistema AI in produzione che elabora dati aziendali deve essere documentato: registro dei trattamenti (GDPR), policy di utilizzo, procedure di audit, documentazione tecnica per eventuali ispezioni. Non è un costo enorme ma è un costo reale, spesso delegato al DPO o al team legale/compliance con un overhead non trascurabile.

Impatto€1k–5k/anno

Il ROI reale: come calcolarlo correttamente

Il ROI del self-hosting (o di qualsiasi sistema LLM) non si calcola solo sui costi — va calcolato sul valore generato. Il valore tipicamente proviene da: riduzione del tempo per task ripetitivi (ore risparmiate × costo orario del personale), riduzione degli errori in processi critici (costo medio di un errore × riduzione del tasso di errore), miglioramento della velocità di risposta (valore del tempo risparmiato per utenti o clienti).

Regola pratica per il ROI

Per giustificare un investimento in self-hosting da €50.000 nel primo anno, il sistema deve generare almeno €50.000 di valore misurabile — equivalente a circa 2.000 ore di lavoro risparmiate a €25/h, o 167 ore/mese. Con 50 utenti che risparmiano in media 3–4 ore/mese grazie al sistema, il ROI è positivo. È un calcolo fattibile — ma va fatto esplicitamente, non assunto.
