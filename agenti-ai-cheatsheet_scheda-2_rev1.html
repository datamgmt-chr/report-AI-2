Leva 01
Prompt Engineering
Comportamento
↺ minuti
"Mostra il comportamento con esempi — non descriverlo con istruzioni."
Sotto-leve
A · Identità e ruolo B · Obiettivo e vincoli C · Ragionamento (CoT) D · Formato output E · Few-shot examples F · Casi limite G · Prompt agentic
Domande chiave
?
Ho definito un ruolo preciso e l'interlocutore a cui l'agente si rivolge?
?
L'obiettivo descrive l'output atteso, non solo il task generico?
?
Ho istruito esplicitamente ogni edge case critico — non solo il caso tipico?
?
Ho esempi few-shot che mostrano il pattern, inclusi casi limite?
Principi chiave
Identità prima: il ruolo guida tutto il resto — definiscilo prima di qualsiasi istruzione.
Un esempio vale dieci regole: un gold standard mostra il confine meglio di qualsiasi descrizione astratta.
Il modello non inferisce le eccezioni: ogni comportamento critico va scritto in modo esplicito.
Attiva sempre — Prima di qualsiasi altra leva
Passa oltre quando il comportamento non migliora nonostante prompt ottimizzato + esempi, o il prompt supera 5K token.
🧠
Leva 02
Scelta del Modello
Qualità base
↺ ore/giorni
"Non si sceglie il modello migliore — si sceglie quello più adatto alle dimensioni critiche del task."
Sotto-leve
Dimensioni critiche Triangolo int./vel./costo Routing per task Valutazione sul proprio task Benchmark vs. golden dataset
Domande chiave
?
Quali sono le 2–3 dimensioni critiche per questo task (ragionamento? velocità? costo? output strutturato)?
?
Ho misurato le prestazioni sul mio task specifico — non solo sui benchmark pubblici?
?
Il mio sistema usa un solo modello dove invece potrei usare routing small/large?
Principi chiave
Task-first: le dimensioni critiche variano per task. Identificale prima di confrontare modelli.
Routing > modello unico: 70% small + 30% large può ridurre i costi del sistema dell'80%.
Il modello non compensa un prompt debole: prima ottimizza il prompt, poi valuta il modello.
Quando attivare
Il profilo capacità/costo/velocità non corrisponde al task. Oppure i costi operativi non sono sostenibili a volume.
🔧
Leva 03
Tool Design
Capacità d'azione
↺ ore
"Esponi intenzioni semantiche, non endpoint tecnici. La description conta più del codice."
Sotto-leve
Nome (verbo_oggetto) Description (cosa/quando/NON quando) Parametri + tipi Output contract Error contract Gerarchia nel prompt Guardrail irreversibili
Domande chiave
?
La description dice quando NON usare il tool — non solo cosa fa?
?
I tool con side effect irreversibili hanno un pattern mostra → verifica → esegui?
?
L'output del tool è pulito e utile per il modello — senza ID tecnici o JSON verboso?
?
Il modello sa cosa fare quando il tool restituisce un errore o un risultato vuoto?
Principi chiave
Il rischio determina l'istruzione: lettura = poca istruzione; comunicazione irreversibile = guardrail ridondanti nello schema E nel prompt.
Ogni azione irreversibile richiede conferma: senza eccezioni.
Wrapper semantici > API dirette: get_customer_info, non salesforce_query.
Quando attivare
L'agente deve interagire con sistemi esterni, eseguire codice, leggere/scrivere dati o inviare comunicazioni.
📚
Leva 04
Knowledge / RAG
Conoscenza
↺ giorni
"Il problema di qualità è quasi sempre nel chunking — non nel modello di retrieval."
Sotto-leve
Chunking strategy Embedding model Vector store + metadati Retrieval (semantico/BM25/ibrido) Re-ranking Augmentation + grounding Eval (recall/faithfulness)
Domande chiave
?
Ogni chunk risponde a qualcosa di utile se letto da solo, senza il resto del documento?
?
Ho istruito il modello su cosa fare quando la risposta non è nel contesto recuperato?
?
Ho misurato recall e faithfulness separatamente — non solo la qualità finale?
?
Uso ricerca ibrida o solo semantica? (Gli ID e i codici tecnici richiedono BM25.)
Principi chiave
Chunking prima di tutto: il 90% dei problemi RAG nasce nella fase di indicizzazione.
Valuta per stadi: recall basso → problema indicizzazione; faithfulness bassa → problema grounding.
RAG per conoscenza, FT per comportamento: non usare il fine-tuning per memorizzare fatti.
Quando attivare
L'agente risponde male per mancanza di conoscenza specifica, aggiornata o del dominio — non per comportamento sbagliato.
🔀
Leva 05
Orchestrazione
Coordinazione
↺ settimane
"Un agente singolo ben configurato batte quasi sempre un sistema multi-agente mal progettato."
Sotto-leve
Loop agentic + terminazione Pattern composizione tool Topologia multi-agente Schema di stato Partial failure + recovery Human-in-the-loop Tracing + debugging
Domande chiave
?
Ogni loop ha un limite massimo di passi e un criterio esplicito di terminazione?
?
Ho uno schema di stato esplicito — non solo gli output dei passi — per gestire i fallimenti parziali?
?
Il sistema multi-agente è davvero necessario, o un singolo agente ottimizzato basta?
?
Ogni richiesta HITL mostra: cosa/chi/livello di rischio/cosa succede se rifiuto?
Principi chiave
Singolo prima di multi-agente: ottimizza fino ai limiti prima di aggiungere complessità.
Lo stato è la mappa: non usare gli output come proxy. Un schema esplicito è il prerequisito per qualsiasi recovery.
Loop senza limite = bug in produzione: il loop infinito non crasha — itera silenziosamente.
Quando attivare
Il task supera le capacità di un singolo turno o richiede coordinazione tra componenti specializzati distinti.
🧪
Leva 06
Testing e Valutazione
Affidabilità
∞ sempre attiva
"Non si migliora ciò che non si misura. La suite di test è più importante del prompt stesso."
Sotto-leve
Suite (tipici/limite/anomali) Dev set + held-out set Metriche per tipo di task Valutazione programmatica LLM-as-judge Valutazione umana Ciclo di iterazione
Domande chiave
?
La suite include ≥30% di casi limite — non solo casi tipici?
?
Ho definito le soglie di accettabilità prima di misurare — non dopo aver visto i dati?
?
Il LLM-as-judge è stato validato su campione umano (correlazione ≥ 0.85)?
?
Dev set e held-out set sono rigorosamente separati — non ho mai ottimizzato sull'held-out?
Principi chiave
Soglie prima di misurare: altrimenti giustifichi qualsiasi risultato a posteriori.
I casi limite rivelano i bug reali: il 60% degli errori in produzione avviene fuori dai casi tipici.
Non è una fase — è un'infrastruttura: ogni modifica a qualsiasi leva va misurata.
Non si "attiva" — è permanente
Va costruita al primo prompt e mantenuta attiva indefinitamente. In parallelo a tutte le altre leve.
💾
Leva M
Gestione Memoria
Continuità
↺ giorni
"Memorizza decisioni e preferenze — non dettagli e contenuto. La memoria minima è la più robusta."
Sotto-leve (4 tipi)
In-context (sessione) Episodica (tra sessioni) Semantica (profilo utente) Procedurale (skill nel prompt) Summarization progressiva Selezione e TTL
Domande chiave
?
Ho una strategia di compressione progressiva prima che il context window saturi?
?
Il profilo semantico viene iniettato all'avvio — e l'input corrente ha sempre la precedenza su di esso?
?
Ogni elemento memorizzato ha un TTL e un meccanismo di aggiornamento/cancellazione?
Principi chiave
4 tipi diversi, 4 meccanismi diversi: non esiste "la memoria" — esiste quella giusta per il problema.
La memoria è un default sovrascrivibile: l'input corrente ha sempre la precedenza sul profilo.
Privacy by design: TTL su tutto, no dati sensibili, diritto alla cancellazione garantito.
Quando attivare
L'agente deve mantenere continuità tra sessioni o la conversazione degrada nelle sessioni lunghe (lost-in-the-middle).
🎓
Leva 07
Fine-tuning
Specializzazione
↺ settimane/mesi
"Il FT insegna come rispondere — non cosa sa. Per conoscenza usa RAG; per comportamento usa FT."
Sotto-leve (3 tipi)
Tipo 1 · Stile e formato Tipo 2 · Ragionamento dominio Tipo 3 · Comportamento / DPO Dataset quality Loss curve + overfitting Test regressione
Domande chiave
?
Ho scritto 10 esempi gold e verificato che nessun prompt riesce a produrli? (Se qualcuno ci riesce, non serve il FT.)
?
Il dataset è abbastanza diversificato — include anche esempi generali per prevenire il catastrophic forgetting?
?
Ho testato la regressione sui task non ottimizzati dopo ogni round di training?
Principi chiave
Parti dal tipo 1: stile → ragionamento → comportamento. Non saltare livelli.
100 esempi eccellenti > 1.000 mediocri: la qualità del dataset determina tutto.
Il FT amplifica — non crea: rafforza pattern già presenti nel modello base, non aggiunge capacità nuove.
Ultima leva — solo dopo aver esaurito le altre
Comportamento sistematicamente sbagliato che prompt + RAG + architettura non riescono a correggere.
