Come usare questa roadmap

La roadmap è strutturata in cinque fasi progressive. Ogni fase ha prerequisiti chiari dalla precedente — saltare fasi è quasi sempre un errore che genera debito tecnico e organizzativo. I tempi sono indicativi per un primo progetto in un'azienda manifatturiera di medie dimensioni senza esperienza AI interna preesistente.

Le checklist nelle fasi sono interattive — cliccabili per tracciare l'avanzamento. Le milestone segnano i gate di passaggio tra una fase e la successiva: prima di proseguire, tutti i criteri della milestone devono essere soddisfatti.

F1
Preparazione e definizione
Prima di scrivere una riga di codice o acquistare hardware
Settimane 1–4
Definire i casi d'uso specifici — non "usare AI", ma "il sistema deve rispondere a domande sui manuali macchina in meno di 10 secondi con accuratezza >85%"
Classificare i dati coinvolti — quali categorie (IP, NDA, dati personali), quale livello di sensibilità, quali restrizioni contrattuali esistenti (usa la matrice del Report B)
Decidere l'architettura di massima — cloud privato vs on-premise vs ibrido (usa la matrice del Report C4)
Calcolare TCO e confrontare con alternative — includere personale, setup, aggiornamenti (usa il simulatore del Report C5)
Identificare il team — chi ha le competenze interne, cosa serve acquisire o formare, se serve un partner esterno
Ottenere approvazione e budget — presentare al management con il business case basato sui KPI identificati
Raccogliere la documentazione tecnica da usare nel sistema RAG — manuali, procedure, specifiche, in qualsiasi formato disponibile
Definire la policy di utilizzo — regole su cosa gli utenti possono e non possono condividere con il sistema (usa la bozza del Report B)

Deployment controllato con un gruppo ristretto di utenti reali
Settimane 11–20

Il problema delle integrazioni: spesso il lavoro più lungo

Il deploy del modello richiede ore o giorni. L'integrazione con i sistemi aziendali esistenti richiede settimane o mesi. È la parte dell'implementazione più spesso sottostimata nel planning iniziale, e quella che genera più sorprese.

Le integrazioni si dividono in due categorie con implicazioni molto diverse: integrazioni read-only (il sistema LLM legge dati da sistemi esistenti per arricchire le risposte) e integrazioni read-write (il sistema LLM scrive su sistemi esistenti, come apertura NC o aggiornamento record). Le integrazioni read-write sono significativamente più complesse da testare, validare e mettere in sicurezza.

ERP (SAP, Microsoft Dynamics, altri) ERP Complessità: Alta

L'integrazione ERP è la più complessa e spesso la più preziosa. Permette all'LLM di rispondere su dati di ordini, produzione, magazzino, fornitori in tempo reale — e potenzialmente di scrivere record (con approvazione umana). Le API ERP sono tipicamente mature ma documentate per sviluppatori ERP, non per sistemi AI.

API REST/OData native BAPI (SAP) Middleware ESB Database view read-only Replica dati su DB intermedio
MES (Siemens Opcenter, Aveva, altri) MES Complessità: Media-Alta

Il MES è la fonte di dati di produzione in tempo reale — stato macchinari, OEE, allarmi, ordini di produzione. L'integrazione read-only per alimentare il contesto dell'agente è spesso più semplice di quanto sembri se il MES espone API REST. L'integrazione in reti OT richiede attenzione specifica alla separazione IT/OT.

API REST MES OPC-UA gateway MQTT broker Database historian Middleware OT/IT
PLM / CAD (Teamcenter, Windchill, altri) PLM Complessità: Media

Il PLM è la fonte primaria di IP industriale — specifiche tecniche, distinte base, revisioni di disegno, cicli di processo. L'integrazione con il sistema RAG permette di rispondere su specifiche tecniche in modo contestualizzato. Attenzione: i documenti PLM contengono spesso l'IP più critico — la classificazione del dato (Report B) deve precedere qualsiasi integrazione.

Export periodico PDF/XML API PLM native Webhook on change File system monitor
Sistema documentale (SharePoint, Confluence, DMS) Documentale Complessità: Bassa-Media

L'integrazione più semplice e spesso il punto di partenza ideale. Manuali, procedure, istruzioni operative, modulistica — tutto ciò che è già in formato testo/PDF è direttamente indicizzabile nel sistema RAG. La maggior parte dei sistemi documentali espone API o connettori standard per l'export.

Microsoft Graph API (SharePoint) Confluence API REST Export cartelle periodico OneDrive/Google Drive connector Email server (per ticket email)
Autenticazione e identità (AD, Azure AD, Okta) Auth Complessità: Bassa

L'integrazione con il sistema di identità aziendale è essenziale per la governance: ogni utente accede con le proprie credenziali aziendali, i permessi sono sincronizzati con i gruppi AD, la revoca degli accessi è automatica al termine del rapporto. Non è opzionale per un sistema in produzione.

SAML 2.0 / SSO OAuth 2.0 / OIDC LDAP / Active Directory Azure AD / Entra ID

Sequenza di integrazione consigliata

Ordine consigliato

1° — Autenticazione (Fase 3): prima di qualsiasi utente reale, l'accesso deve essere gestito con credenziali aziendali. È il fondamento della governance.

2° — Sistema documentale (Fase 3): la fonte di dati più semplice da integrare e quella che alimenta il sistema RAG. Alta priorità, bassa complessità.

3° — MES read-only (Fase 4): dati di produzione in tempo reale per gli agenti di supporto operatori. Complessità media, ma valore alto per i casi d'uso manifatturieri.

4° — ERP read-only (Fase 4): dati di ordini, magazzino, fornitori. Complessità alta — pianificare almeno 6–8 settimane per un'integrazione ERP anche semplice.

5° — PLM (Fase 4, con attenzione alla sicurezza dati): solo dopo aver verificato la classificazione dei dati PLM e implementato i controlli di accesso granulari.

Integrazioni write (ERP/MES/qualità) — Fase 4-5, con HITL obbligatorio: scrivere su sistemi aziendali è una fase successiva che richiede validazione estesa e human-in-the-loop per ogni azione.

Il team minimo per un progetto self-hosted

Non esiste un team "standard" — dipende dalla complessità del progetto, dall'architettura scelta e dalle competenze già presenti. Ma esistono ruoli che devono essere coperti, internamente o con partner esterni. La mancanza di anche uno solo di questi ruoli è un rischio di progetto significativo.

Per un primo progetto self-hosted di livello medio (sistema RAG in produzione, 50–150 utenti, integrazione con 1–2 sistemi), il team minimo efficace è di 3–4 persone con commitment part-time, più il supporto di un partner esterno per le competenze mancanti.

Gap comuni e come colmarli

Il gap più frequente è la competenza MLOps/AI Engineering. Tre opzioni per colmarlo, in ordine di preferenza:

Formazione interna: se c'è un profilo IT con buone basi Python e DevOps, 2–3 mesi di formazione focalizzata (LLM deployment, LangChain/LlamaIndex, vector database) possono essere sufficienti per un primo progetto. Costo basso, tempo medio, risultato stabile nel lungo periodo.

Assunzione: un MLOps engineer ha tipicamente un costo di €50.000–80.000/anno. Si giustifica se il progetto è strategico e continuativo. Time-to-hire 2–4 mesi nel mercato attuale.

Partner esterno: per il primo progetto, un system integrator o una software house specializzata in AI può coprire le competenze mancanti. Il rischio principale è la dipendenza — pianificare un percorso di knowledge transfer esplicito nel contratto.

Quando serve un partner esterno

Indicatori che giustificano un partner

· Nessuno in azienda ha mai deployato un LLM o costruito un sistema RAG
· Il progetto ha una scadenza stretta (meno di 3 mesi al go-live)
· L'integrazione coinvolge sistemi ERP complessi con poca documentazione API
· Si vuole on-premise con cluster GPU multipli già dal primo progetto
· Il caso d'uso coinvolge agenti con azioni su sistemi critici (es. scrittura ERP)

In tutti questi casi: selezionare un partner con referenze specifiche in ambito manifatturiero e LLM, non solo in AI generica. Inserire nel contratto: knowledge transfer documentato, formazione del team interno, codice sorgente e documentazione di proprietà del cliente.

Come misurare il successo: il framework in tre livelli

Un sistema LLM ha tre livelli distinti di performance, ognuno con metriche specifiche. Un sistema eccellente a livello tecnico ma non adottato dagli utenti è un fallimento. Un sistema molto usato ma che produce risposte errate è un rischio. Un sistema usato e tecnicamente corretto, ma che non migliora i processi aziendali, non giustifica l'investimento.

Le metriche vanno raccolte in modo continuativo — non solo al lancio. Il sistema cambia nel tempo (modello aggiornato, documenti aggiunti, nuovi utenti) e le metriche possono degradare silenziosamente senza un monitoring attivo.

KPI tecnici: il sistema funziona?

Il dashboard di monitoring minimo

Setup minimo consigliato

Prometheus + Grafana per le metriche tecniche (latenza, uptime, utilizzo GPU) — setup in 1–2 giorni con i template standard per vLLM/Ollama.

Log strutturati con query, user_id, latency, rating per le metriche di utilizzo — un CSV o database semplice è sufficiente all'inizio.

Survey mensile breve (3 domande max) agli utenti per le metriche di soddisfazione — non automatizzabile ma essenziale.

Benchmark mensile automatizzato — script che esegue il set di test definito in Fase 2 e salva i risultati. Alert se l'accuratezza scende sotto soglia.

I rischi che affondano i progetti LLM

I progetti di implementazione LLM falliscono per ragioni ricorrenti — non tecniche, nella maggior parte dei casi. Il modello non è abbastanza capace è solo il quinto o sesto motivo più frequente. I primi quattro sono quasi sempre organizzativi o di governance.

Il risk register qui sotto è basato sui pattern più comuni osservati in implementazioni enterprise. Per ogni rischio è indicato un livello di probabilità, l'impatto potenziale e le mitigazioni specifiche.

Casi d'uso non definiti o cambiati in corso

Il progetto parte con obiettivi vaghi ("usiamo l'AI"), il modello viene deployato prima di capire cosa deve fare, e si scopre in produzione che le aspettative degli utenti non coincidono con quanto costruito. Mitigazione: milestone F1 non negoziabile — nessun PoC prima di avere casi d'uso misurabili e approvati.

Mancanza di competenze MLOps interne

Il sistema viene deployato da un consulente esterno senza knowledge transfer adeguato. Il consulente termina il progetto e nessuno in azienda sa come gestire aggiornamenti, problemi o modifiche. Mitigazione: knowledge transfer esplicito nel contratto, formazione del team interno come deliverable, documentazione tecnica completa di proprietà del cliente.

Qualità della documentazione insufficiente

Il sistema RAG viene costruito su documentazione incompleta, non aggiornata o in formati non processabili (PDF scansionati non OCR, disegni CAD, formati proprietari). La qualità delle risposte è inaccettabile non per il modello ma per i dati. Mitigazione: audit della documentazione disponibile in Fase 1, prima di scegliere il caso d'uso — non tutte le documentazioni sono immediatamente indicizzabili.

Resistenza degli utenti all'adozione

Il sistema viene percepito come uno strumento di controllo, come una minaccia al proprio ruolo, o semplicemente come complicato rispetto alle soluzioni già in uso (ricerca su Google, colleghi). Mitigazione: coinvolgere gli utenti finali dal design, non dall'adozione. Mostrare il valore diretto per il loro lavoro. Partire con i casi d'uso più utili per chi lo usa, non per chi lo commissiona.

Integrazione con sistemi legacy più complessa del previsto

Le API del sistema ERP o MES non sono documentate, cambiano tra versioni, o richiedono competenze specifiche non disponibili. Il tempo di integrazione si triplica rispetto alle stime. Mitigazione: discovery tecnica delle API disponibili prima di pianificare le integrazioni, stima con buffer del 100% per integrazioni legacy, fallback su export periodico dove le API non sono percorribili.

Medio

Costi reali superiori alle stime iniziali

Il TCO viene calcolato correttamente sull'hardware ma non include personale, integrazioni, formazione e manutenzione. Il management approva un budget che si rivela insufficiente a metà progetto. Mitigazione: usare il modello di costo completo del Report C5, includere tutte le voci, e aggiungere un contingency del 30% per il primo progetto.

Mitigazione: DPO coinvolto dalla Fase 1, classificazione dati completata prima del PoC, policy di utilizzo comunicata prima dell'accesso al sistema.

Criteri go/no-go espliciti

Quando fermarsi e rivalutare

Stop dopo Fase 1 se: non si riesce a definire un caso d'uso con metriche di successo misurabili · il budget approvato è inferiore al TCO realistico · non c'è nessuno in azienda o tra partner che conosce il deployment di LLM

Stop dopo Fase 2 (PoC) se: la qualità misurata è significativamente sotto la soglia definita e non migliora con ottimizzazioni · gli utenti del pilota non vedono valore concreto nel sistema · il caso d'uso si rivela in Zona Rossa per capability (vedi Report C2)

Ridimensionare dopo Fase 3 se: l'adozione è molto bassa nonostante la qualità tecnica buona · il ROI misurato è negativo dopo 6 mesi di produzione · i costi operativi superano le stime del 50%+

Fermarsi non è fallire — è governare razionalmente un progetto. Un PoC che dimostra che il self-hosting non è la soluzione giusta per quel caso d'uso è un risultato di valore, non una perdita.

Il percorso decisionale distillato

Se dovessimo ridurre l'intera serie a un percorso decisionale sintetico, sarebbe questo:

In ordine, prima di tutto il resto

1. Definisci il caso d'uso con metriche. Non "vogliamo usare l'AI". Cosa deve fare, per chi, con quale qualità misurabile. Senza questo, tutto il resto è prematuro.

2. Classifica i dati coinvolti. IP industriale critico, dati sotto NDA, dati personali? Questo determina se il self-hosting è necessario o se un piano enterprise è sufficiente.

3. Verifica la capability con un test diretto. Prima dell'infrastruttura, testa il modello sul tuo caso d'uso reale. Usa il metodo del Report C2. I benchmark pubblici non sostituiscono il test sui tuoi dati.

4. Calcola il TCO completo. Hardware o cloud, personale, setup, integrazioni, aggiornamenti. Confronta con il costo di un piano enterprise API. La scelta economica potrebbe sorprenderti.

5. Inizia piccolo e misura. PoC su cloud privato, caso d'uso circoscritto, gruppo pilota di 10–20 utenti, KPI definiti prima del lancio. Espandi solo se i dati lo giustificano.

Connessione con il contesto più ampio

Questa serie si è sviluppata all'interno di un percorso più ampio iniziato nelle chat precedenti — dalla comprensione degli agenti AI, alle architetture multi-agent, fino alla sicurezza dei dati e al self-hosting. I temi sono connessi: un sistema self-hosted ben progettato è la base infrastrutturale su cui costruire agenti AI sicuri, che a loro volta abilitano i casi d'uso di automazione industriale discussi nella serie sugli agenti.

Il passo naturale successivo — non ancora esplorato — è la convergenza tra sistemi agentici e processi produttivi reali: come gli agenti si integrano con i sistemi di controllo, come si gestisce la supervisione umana su agenti che interagiscono con macchinari, e quali sono i requisiti di affidabilità per sistemi AI in contesti di sicurezza funzionale. È un territorio ancora in evoluzione rapida, con implicazioni sia tecniche che normative (AI Act europeo, IEC 61511 per la sicurezza funzionale).
