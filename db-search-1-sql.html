Il meccanismo base
Come un agente trasforma un prompt in una query SQL

Quando un utente chiede "mostrami i prodotti outdoor disponibili sotto i 200 euro", non sta scrivendo una query — sta descrivendo in linguaggio naturale un insieme di criteri. Il compito dell'agente è tradurre questa descrizione in qualcosa che il database capisce: una query SQL precisa, con nomi di colonne reali, operatori corretti, valori nel formato atteso.

Questo processo si chiama text-to-SQL. Non è magia — è una forma di traduzione da un linguaggio (il linguaggio naturale) a un altro (SQL), e come ogni traduzione funziona bene quando il traduttore conosce entrambe le lingue. Il modello LLM conosce bene SQL in senso astratto; quello che non conosce è il vocabolario specifico del tuo database: come si chiama la colonna del prezzo, quali sono i valori esatti della colonna categoria, se "disponibile" è un booleano o una stringa.

Il ciclo text-to-SQL — dalla richiesta al risultato
1
Input
La richiesta in linguaggio naturale
"Mostrami i prodotti outdoor disponibili sotto i 200 euro, ordinati per prezzo crescente."
2
Contesto
L'LLM riceve lo schema del database
Nome delle tabelle, colonne, tipi di dato, valori validi per i campi codificati. Senza questo, il modello non può costruire una query corretta — inventerebbe nomi di colonne che non esistono.
3
Traduzione
L'LLM genera la query SQL
Il modello mappa ogni concetto del prompt sui campi e valori del database: "outdoor" → categoria = 'abbigliamento-outdoor', "disponibili" → disponibile = true, "sotto i 200 euro" → prezzo < 200.
4
Esecuzione
Il runtime esegue la query sul database
L'agente passa la query generata al database. I risultati tornano come righe strutturate che il modello usa per costruire la risposta finale.

Il passo più critico è il 3 — la traduzione. E il punto più fragile della traduzione è il mapping tra concetti del prompt e valori del database. "Outdoor" nel prompt corrisponde a 'abbigliamento-outdoor' nel database? O a 'outdoor'? O a 'Outdoor & Sport'? Il modello non lo sa — a meno che tu non glielo dica.

Il principio di base
Un LLM conosce SQL. Non conosce il tuo database. Tutto ciò che è specifico del tuo schema — nomi, tipi, valori — deve essere comunicato esplicitamente nel contesto.
Il contesto necessario
Cosa fornire all'LLM: schema, valori, significati

Per fare text-to-SQL in modo affidabile, il modello ha bisogno di tre livelli di informazione sul database. Ognuno risolve un problema diverso.

Tabella di esempio — prodotti

Guardando questa tabella, emergono tre livelli di informazione che servono al modello:

I tre livelli di contesto — cosa risolvono
1
Schema — nomi e tipi
Nomi esatti delle colonne, tipi di dato, struttura della tabella. Obbligatorio. Senza di esso il modello inventa nomi di colonne che non esistono — generando query che falliscono silenziosamente o con errore.
Risolve: "Non so come si chiama la colonna del prezzo"
2
Valori validi per i campi codificati
L'elenco completo dei valori possibili per ogni campo a vocabolario chiuso. Obbligatorio per i campi chiusi. Senza di esso il modello usa valori plausibili ma sbagliati — 'outdoor' invece di 'abbigliamento-outdoor'.
Risolve: "Non so il valore esatto da usare nel WHERE"
3
Significati e mapping semantico
Spiegazione del significato di ogni valore codificato — cosa include, sinonimi comuni, casi limite. Necessario quando il vocabolario del prompt diverge dal vocabolario del database. Senza di esso il modello non sa che "giacche" corrisponde a 'abbigliamento-outdoor'.
Risolve: "Non so quale valore corrisponde al concetto espresso nel prompt"

I livelli 1 e 2 sono sempre necessari. Il livello 3 è necessario quando c'è un divario semantico tra il linguaggio del prompt e i valori del database — il che accade quasi sempre con i campi a valori codificati non ovvi.

Come si fornisce questo contesto in pratica

Il modo più semplice e robusto è includere lo schema come testo strutturato nel system prompt dell'agente. Non serve un formato sofisticato — basta che sia leggibile e completo:

Tabella: prodotti
- categoria (VARCHAR): valori possibili: 'abbigliamento-outdoor' (giacche, pantaloni, pile per uso esterno), 'abbigliamento-sport' (abbigliamento per sport indoor e palestra), 'accessori' (zaini, guanti, cappelli), 'calzature', 'equipment' (attrezzatura tecnica)

Il livello di dettaglio nel mapping semantico dipende da quanto è intuitivo il vocabolario del database. Se i valori sono autoesplicativi ('true' / 'false'), bastano i valori. Se sono codici o etichette opache ('CAT-01', 'abbigliamento-outdoor'), serve la spiegazione.

Il caso più comune e più insidioso
Campi a valori codificati: il problema del vocabulary mismatch

Un campo a valori codificati — categoria, stato, tipo, stagione — sembra il caso più semplice: ha un numero finito di valori, basta elencarli. Ma è anche il caso dove gli errori di traduzione sono più frequenti e più silenziosi.

Il problema è il vocabulary mismatch: il prompt usa parole diverse dai valori del database. L'utente dice "giacche invernali" — il database ha 'abbigliamento-outdoor' e 'autunno-inverno'. Il modello deve capire che "giacche invernali" corrisponde a quella combinazione di valori — e lo fa solo se gli viene detto esplicitamente come sono strutturate le categorie.

Vocabulary mismatch — esempi di prompt e mappings necessari
Prompt dell'utente Concetto espresso Valore nel database Mapping ovvio?
"prodotti outdoor" abbigliamento per uso esterno categoria = 'abbigliamento-outdoor' Parzialmente — dipende da come il modello interpreta "outdoor"
"giacche e pantaloni da montagna" specifici capi outdoor categoria = 'abbigliamento-outdoor' No — "montagna" non è una categoria, è un contesto d'uso
"roba invernale" prodotti per stagione fredda stagione = 'autunno-inverno' Parzialmente — il modello potrebbe anche cercare parole come "invernale" nel nome
"prodotti disponibili subito" in stock disponibile = true Sì — "disponibile" è semanticamente vicino a true
"articoli esauriti" non in stock disponibile = false Sì — con il mapping dei valori booleani
"scarpe e stivali" calzature categoria = 'calzature' Parzialmente — il modello potrebbe non sapere che "stivali" è in questa categoria
"attrezzatura tecnica" equipment categoria = 'equipment' No — senza spiegazione "equipment" è opaco, il modello potrebbe usare 'abbigliamento-sport'

Il pattern che emerge: i mapping che sembrano ovvi spesso non lo sono per il modello, perché il modello non conosce la logica interna con cui le categorie sono state definite nel tuo database specifico. "Equipment" come categoria che include zaini ma non giacche — chi ha progettato il database lo sa, il modello no.

Come strutturare il mapping semantico nel prompt

Per ogni campo a valori codificati, fornisci: il nome del campo, l'elenco dei valori, e per ogni valore una riga di spiegazione con esempi di cosa include e i sinonimi comuni che un utente potrebbe usare.

Esempio efficace:

categoria: classificazione merceologica del prodotto
'abbigliamento-outdoor': giacche, pantaloni, pile, softshell — capi per attività all'aperto (trekking, alpinismo, sci)
'abbigliamento-sport': magliette tecniche, pantaloncini, leggings — per attività sportive indoor
'accessori': zaini, guanti, cappelli, imbracature, corde, bastoni
'calzature': scarpe, stivali, scarponi, sandali da trekking
'equipment': tende, sacchi a pelo, fornelletti, materassini

Con questo contesto, il modello può mappare correttamente "giacche da montagna" su 'abbigliamento-outdoor' e "corde" su 'accessori'.

Il caso delle categorie sovrapposte

Un problema frequente: categorie che si sovrappongono semanticamente. "Giacca da running" — è 'abbigliamento-outdoor' o 'abbigliamento-sport'? Se il database non ha una regola chiara, il modello ne applicherà una sua — e sarà imprevedibile.

La soluzione: documenta esplicitamente i casi limite nel mapping. "Nota: le giacche da running e ciclismo sono in 'abbigliamento-sport', non in 'abbigliamento-outdoor', anche se usate all'esterno." Questo è il tipo di conoscenza implicita che il modello non può inferire — deve trovarsela scritta.

Il caso più sottovalutato
Testi chiusi con variazioni: normalizzazione e ambiguità

C'è una categoria di campo che si comporta come un valore codificato ma ha la forma di un testo libero: lo stato di un ordine, il nome di un fornitore, la descrizione di un processo. In teoria ha un vocabolario finito; in pratica i valori non sono standardizzati — lo stesso concetto appare scritto in modi diversi da operatori diversi, in momenti diversi, con convenzioni diverse.

Il problema della non-uniformità — stessa colonna, stesso concetto, valori diversi
Campo: stato_ordine — valori reali trovati nel database
'In lavorazione'
'in lavorazione'
'lavorazione in corso'
'IN LAVORAZIONE'
'lavoraz.'
'Processing'
6 modi diversi per lo stesso stato. Un WHERE stato_ordine = 'In lavorazione' troverebbe solo 1 su 6.
Come gestirlo — due approcci
Approccio A — ILIKE e pattern matching
WHERE LOWER(stato_ordine) LIKE '%lavorazi%'
Trova tutte le varianti senza normalizzare i dati. Fragile se le varianti sono molto eterogenee.
Approccio B — mapping esplicito nel prompt
Fornire al modello la lista di tutte le varianti note per ogni concetto: "stato 'in lavorazione' può apparire come: 'In lavorazione', 'lavorazione in corso', 'IN LAVORAZIONE', 'lavoraz.', 'Processing'. Usa LOWER(stato) LIKE '%lavorazi%'".

La soluzione definitiva per questo problema non è nel prompt — è nel database. Dati non uniformi producono query fragili indipendentemente da quanto sia buono il modello. Ma in attesa di una pulizia dei dati, il prompt può fornire al modello le varianti note e le strategie di ricerca robuste.

Il testo chiuso corto — un caso speciale

C'è un tipo di campo che merita attenzione separata: il testo corto con contenuto semantico ma vocabolario parzialmente aperto. Esempi: il campo "note" di un ordine con frasi come "cliente VIP", "urgente", "spedizione express richiesta". Non è un valore codificato fisso, ma non è nemmeno un testo aperto narrativo.

Per questi campi, il full-text search con ILIKE funziona spesso bene per parole chiave specifiche. Il rischio è che il modello provi a fare inferenze semantiche — cercando "urgente" quando il prompt dice "prioritario" — e fallisca perché il campo non è abbastanza ricco per il retrieval semantico. La regola pratica: se il campo ha meno di 20 parole in media, usa keyword search; se ha più di 50 parole, considera il retrieval semantico.

Il confine
Quando SQL non basta: il limite strutturale del testo aperto

SQL è uno strumento straordinario per i dati strutturati. Ma ha un limite preciso: lavora su corrispondenze, confronti e pattern — non sul significato. Quando la ricerca richiede di capire il significato di un testo, SQL non è la soluzione giusta.

SQL funziona bene — questi casi

"Prodotti con prezzo tra 100 e 300 euro" → WHERE prezzo BETWEEN 100 AND 300

"Giacche disponibili in magazzino" → WHERE categoria = 'abbigliamento-outdoor' AND disponibile = true

"Ordini degli ultimi 30 giorni" → WHERE data_ordine > NOW() - INTERVAL '30 days'

"Prodotti con 'merino' nel nome" → WHERE LOWER(nome) LIKE '%merino%'

"Tutto tranne la categoria calzature" → WHERE categoria != 'calzature'

SQL non funziona — questi casi

"Prodotti adatti all'alta montagna" → non è un campo, è un concetto nella descrizione

"Giacche con materiali tecnici di qualità premium" → qualità e premium sono valutazioni soggettive nel testo

"Articoli pensati per clienti professionisti" → l'uso previsto è nella descrizione, non in una colonna

"Prodotti simili a questo che ho già visto" → similarità semantica tra descrizioni

"Capi resistenti e durevoli" → durabilità non è una colonna — è un concetto distribuito nella scheda

Il confine tra "SQL basta" e "SQL non basta" non è la lunghezza del testo — è la natura della corrispondenza cercata. Se cerchi un valore specifico o un pattern testuale, SQL funziona. Se cerchi un concetto che potrebbe essere espresso in molti modi diversi nel testo, hai bisogno di qualcosa che capisca il significato.

Il confine che conta
SQL cerca corrispondenze. Il retrieval semantico cerca significati. Quando la domanda è "trova le righe che hanno questo valore", SQL è la risposta. Quando la domanda è "trova le righe che parlano di questo concetto", serve qualcosa di più.
